# z-ai/glm-5.3-flash

## Findings (most severe first)

**1. HIGH — sgs-check-containers.sh:7,11 — bind mounts of host paths other than docker.sock are not flagged.**
The Mounts check only matches `docker\.sock`. `docker run -v /:/host alpine` (or `-v /etc:/etc`, `-v /home:/home`) gives the container root read/write over the whole host filesystem and is reported as clean. Fix: flag any `.Mounts[].Source` that is an absolute host path outside `/var/lib/docker/volumes/` — at minimum `/`, `/etc`, `/var`, `/root`, `/home`, `/run`.

**2. HIGH — sgs-check-containers.sh:6-13 — `--ipc=host` is not flagged.**
A container with `--ipc=host` shares the host IPC namespace: it can read and write every local user's `/dev/shm`, which on an ML box holds NCCL shared buffers, DataLoader shared-memory segments and memmapped tensors of *other users*. That is cross-user data compromise with a one-line docker command, and the check passes. Fix: add `if ($3 == "host") …` style test on `.HostConfig.IpcMode == "host"` (also flag `IpcMode` naming another container's namespace only if that container is privileged).

**3. MEDIUM — sgs-check-containers.sh:6-13 — several other root-equivalent settings are unchecked.**
Not flagged: `--security-opt seccomp=unconfined` / `apparmor=unconfined` (`.HostConfig.SecurityOpt`), `--device /dev/kvm` or any host block device (`.HostConfig.Devices`, `.HostConfig.DeviceRequests` aside), `--cap-add=DAC_READ_SEARCH|DAC_OVERRIDE` (with any bind mount that reads arbitrary host files), `--cgroupns=host`. A container with only `seccomp=unconfined` + default caps can use `mknod`/`kcore`-style escapes the current four checks never see. Fix: extend the inspect template with `{{.HostConfig.SecurityOpt}}`, `{{.HostConfig.Devices}}`, `{{.HostConfig.CgroupnsMode}}` and broaden the CapAdd regex to the dangerous-cap list.

**4. MEDIUM — sgs-check-ssh.sh:5,19 — `sshd -T` reports the config files, not the running daemon.**
Scenario: the stack writes `sshd-10-sgs.conf`, but `systemctl reload/restart ssh` fails (or the socket-activated daemon was started before the file landed and is never restarted). `sshd -T` prints `passwordauthentication no` → PASS, while the live sshd still accepts passwords. Also, `sshd -T` without `-C` shows only main-section values; a `Match Group admins` block setting `X11Forwarding yes` / `PasswordAuthentication yes` is invisible → false PASS. Fix: after reading settings, compare against the running process (`systemctl cat ssh` + check for a successful reload, or `sshd -T -C user=<callinguser>,host=localhost,addr=127.0.0.1`), and grep the effective config for `Match` blocks overriding the audited keywords.

**5. MEDIUM — sgs-check-sandbox.sh:5-7 — the score check passes weakenings that don't move the score out of the "OK" band, including auth/socket changes.**
Two concrete bypasses: (a) a drop-in setting `PrivateTmp=no` or clearing `RestrictSUIDSGID`/`NoNewPrivileges` can keep the overall score under 4.0 ("OK") while genuinely weakening the sandbox (exact scores unverified, but the band check is the only gate); (b) more importantly, a drop-in overriding `ExecStart` (clear + re-set) to add `--ServerApp.sock_mode=0666` or `--ServerApp.allow_unauthenticated_access=True` changes nothing systemd-analyze measures — the check prints "sandbox is in place" while every local user can now reach Jupyter without a token. Fix: additionally verify the runtime socket mode (`stat -c %a /run/sgs-jupyter/*/jupyter.sock` == 600) and diff the effective unit (`systemctl cat`) against the shipped ExecStart/directives instead of relying on the score alone.

**6. MEDIUM — sgs-check-sandbox.sh:4 — only *active* units are audited.**
`systemctl list-units --state=active` misses units that are enabled but stopped (user hasn't started Jupyter yet) or in failed state. The daily timer will frequently run at a time when no `sgs-jupyter@*` unit is active, so a planted weakening drop-in sits undetected until the next check that happens to coincide with an active unit. Fix: use `systemctl list-unit-files 'sgs-jupyter@*' --state=enabled` plus `systemd-analyze security` on the template, or run the check at login for the logging-in user's unit.

**7. MEDIUM — sgs_cuda_preload.py:96-97 — the JAX CPU fallback is baked into long-lived parent processes and inherited stale.**
The check runs once at interpreter startup and sets `JAX_PLATFORMS=cpu` in `os.environ`. The `sgs-jupyter@.service` server process starts at boot; if the NVIDIA driver is not yet loaded at that moment (manual `modprobe`, driver installed without reboot, module autoload deferred), the server's environment is pinned to `cpu` and *every kernel it spawns later* — after the driver is up — inherits `JAX_PLATFORMS=cpu`, so JAX silently trains on CPU with no error. Fix: don't export from the server; do the check in the kernel-spawn path (e.g., set it in a kernel-launch wrapper or `KernelSpec` env hook) so each kernel re-evaluates `/proc/driver/nvidia/version` at its own startup.

**8. MEDIUM — sgs-jupyter@.service:58,61-69 — InfiniBand/RDMA NCCL is broken by both the syscall filter and the device list.**
`RestrictAddressFamilies` omits `AF_IB` (NCCL's IB transport opens AF_IB sockets), and no `DeviceAllow` covers `/dev/infiniband/uverbs*`. On a multi-node IB cluster (Lambda/other cloud IB instances), `torchrun`/NCCL launched from a notebook falls back to TCP or aborts with `NCCL WARN` — the exact multi-node workflow the stack advertises. Fix: add `AF_IB` to line 58 and `DeviceAllow=char-infiniband-uverbs rw` (and `char-infiniband` for umad/rdma_cm if needed).

**9. MEDIUM (unverified) — sgs-jupyter@.service:64 — `char-nvidia-caps` is read-only, which likely breaks MIG compute.**
MIG device nodes (`/dev/nvidia-caps<N>`) are opened read-write by CUDA for compute; with `DeviceAllow=char-nvidia-caps r`, `nvidia-smi -q` works but a notebook kernel cannot run on a MIG instance. Fix: `DeviceAllow=char-nvidia-caps rw` (the caps interface is not a privilege boundary the way the IMEX channels are; if concerned, allow rw only for the compute minors).

**10. LOW — sgs-jupyter@.service:52,56 — deliberate-but-undocumented workflow breaks.**
`RestrictNamespaces=yes` blocks `unshare(CLONE_NEWUSER)` → rootless podman/buildah and any `unshare -Ur` debugging from a notebook fail; `@mount` in the filter blocks `mount()` → FUSE mounts (rclone, gdrive-fuse) fail; `PrivateTmp=yes` breaks tools that hand off files via `/tmp` to a host service. None of these are security defects, but they will be filed as "stack broke my workflow" bugs. Fix: document them in the service header next to the MemoryDenyWriteExecute/RemoveIPC notes.

**11. LOW — sgs-check-containers.sh:6 — silent PASS when Docker is absent or unreachable.**
If the docker CLI is missing, the daemon is down, or the checker runs unprivileged without docker-group membership, `docker ps` fails, `risky` is empty, and the block prints nothing — not even a skip. A machine with a root-equivalent container is reported clean. Fix: distinguish "no containers" (`docker ps -q` succeeded, empty) from "couldn't check" and emit `skip`/`bad` accordingly.

**12. LOW (unverified) — sgs-check-sandbox.sh:5 — output parsing assumes the emoji/field layout of current systemd.**
`awk '{ print $(NF-2), $(NF-1) }'` assumes the trailing emoji is the last field. Under `LC_ALL=C` (or a systemd build/version that omits or changes the trailing glyph), the offsets shift — e.g. `…: 2.2 OK` yields `unit: 2.2`, which matches neither `*OK*` nor `*SAFE*` and produces a false "sandbox is weakened" (or, with different layouts, could match `*OK*` spuriously). Fix: match the score and verdict with a regex on the line (`awk '/Overall exposure level/ { for (i=1;i<=NF;i++) if ($i ~ /^[0-9]+\.[0-9]+$/) { print $i, $(i+1) } }'`) instead of counting fields from the end.

No issue found with: the token-generation/grep logic in `sgs-jupyter@.service:27`, the `_PreloadingLoader` meta-path hook (correctly scoped to real `import tensorflow` executions), the `char-nvidia-uvm`/`char-drm`/ptmx device allows, the `@clock @module @mount …` filter groups with respect to Triton/torch.compile/numba (JIT needs only writable memory, which is intentionally permitted), CUDA IPC (uvm + /dev/shm both available), or the sshd `10-` precedence claim for Ubuntu 24.04's `Include` placement.
