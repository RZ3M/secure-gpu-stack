# z-ai/glm-5.3-flash

## Findings (most severe first)

**1. High — `sgs-gpu-devices` has no `set -e` and no error checks, so failures report success.**
`files/sgs-gpu-devices:41-46`: if `chown`/`chmod`/`mknod`/`mount` fail (e.g. the node is replaced between the `stat` on line 41 and the `chown`, or `mount --bind` returns EBUSY), the script continues and exits 0. `install_driver.sh:73` (`|| die`) then never fires, and the installer prints "GPU device files: video group only" with a 0666, unlocked device. Fix: `set -e` (guarding the intentional `mounted()`/`case` non-matches), and re-`stat` each device at the end, failing if any is not `0:$gid:660` *and* ro-mounted.

**2. High — `unlock()` spins forever on EBUSY.**
`files/sgs-gpu-devices:26`: `while mounted; do umount; done` has no failure handling. `umount` of a bind mount fails with EBUSY while any process holds the file open — and `nvidia-persistenced` holds `/dev/nvidiactl` open permanently. Scenario: video GID changes, or a UVM major change while a CUDA process is alive → `umount` EBUSY → infinite loop → systemd kills the oneshot at `TimeoutStartSec` (90s), the device stays wrong, and `install_driver.sh:73` dies. Fix: bound retries with `logger` on failure, and stop `nvidia-persistenced` (or use `umount -l` + relock) before unlocking a device that may be open.

**3. Medium — the lock is per-mount, not per-inode; any other rw mount of the inode defeats it.**
The EROFS you observed applies only to the ro bind mount itself. Any root process (including root in a GPU container, which has a bind of the same inode via `--gpus`/CDI) can do `mount --bind /dev/nvidiactl /tmp/x; mount -o remount,bind,rw /tmp/x; chmod 0666 /tmp/x` — the devtmpfs superblock is rw, so the chmod succeeds and changes the *host* inode mode; host users then get read opens through the ro mount. This also chains into finding 2 (next `sgs-gpu-devices` run needs `unlock` while the file is open). Whether Docker's own device bind clones the ro flag is **unverified**; the explicit rebind path above is not. Fix: document/enforce that GPU containers must not be privileged, and have `sgs-check` also compare the mount's `major:minor` (mountinfo field 3) against the device so a stale/pinned mount is caught.

**4. Medium — the udev rule's DEVPATH match likely never fires.**
`files/72-sgs-nvidia-devices.rules:5`: driver-bind uevents are emitted on the *PCI device* (`DEVPATH=/devices/pci.../...`), not on `/bus/pci/drivers/nvidia`; `DEVPATH=="/bus/pci/drivers/nvidia"` looks like it can never match a device uevent. If so, the driver-load trigger is dead and locking after a module (re)load depends entirely on the `nvidia_uvm` rule and `nvidia-cdi-refresh`. **Unverified** (I can't test the uevent shape here); verify with `udevadm test $(udevadm info -q path -n /sys/bus/pci/devices/<addr>)` or `udevadm monitor`. Fix: match `ACTION=="bind", SUBSYSTEM=="pci", ENV{DRIVER}=="nvidia"` the way Ubuntu's 71 rule does.

**5. Medium — race: the service can run before the device nodes exist, then never re-runs.**
`files/sgs-gpu-devices:30` skips missing nodes and exits 0. `SYSTEMD_WANTS` only queues an async job; if it wins against udev's own `mknod` from `71-nvidia.rules` (or the driver-bind event fires before the chardev nodes are created), the script does nothing, Ubuntu's rule then creates `/dev/nvidia-uvm` 0666, and no further event re-triggers until `nvidia-cdi-refresh`. That is the same create-race the redesign was meant to close. Fix: in the script, wait/retry briefly for each expected node (e.g. a few hundred ms of retries), and/or add `KERNEL=="nvidia*"`, `KERNEL=="nvidia-uvm*"` device matches to the rule so node-creation events also trigger it.

**6. Medium — partial lock failure is sticky: rw bind is never upgraded to ro.**
`files/sgs-gpu-devices:46`: if `mount --bind` succeeds but `remount,bind,ro` fails (e.g. transient EBUSY), the device is left rw-bind-mounted. Every later run sees `mounted()` true and skips line 46 entirely, so it stays unlocked forever; only `sgs-check` notices. Fix: make `mounted()` (line 25) check for `ro` in `$6` like `sgs-check-driver-block.sh:32` does, and retry the remount when mounted-but-not-ro.

**7. Medium — `sgs-check` false PASS: the ro check doesn't verify the mount is of the device it names.**
`sgs-check-driver-block.sh:32` matches only on mountpoint (`$5`) and `ro` in `$6`. A stale ro mount pinned on a replaced inode (possible after the UVM replacement path at `sgs-gpu-devices:34-38` if a second stale mount exists, or after manual fiddling) satisfies the check while the live node is unprotected. Fix: also require mountinfo field 3 (`$3`) to equal the device's `major:minor` (`stat -c '%t:%T'`), matching what `mounted()` should do too.

**8. Low — `install_driver.sh:42` sed can silently no-op.**
`s/NVreg_DeviceFileGID=44 /.../ ` requires a trailing space; if the shipped `modprobe-sgs-nvidia.conf` ends the line at `44`, the GID is never rewritten, the driver creates nodes with GID 44, and line 55's `DeviceFileGID: $vgid` check fails → spurious `NEED_REBOOT` on every install (or, if GID 44 ≠ video, wrong group until the relock). Fix: drop the trailing space from the pattern or verify the substitution happened (`grep -q "NVreg_DeviceFileGID=$vgid"` after sed, else die).

**9. Low — `install_driver.sh:47` masks enable failure.**
`[ ... ] && systemctl enable ... || true`: if `systemctl enable nvidia-fabricmanager` fails, `|| true` hides it and Fabric Manager never starts at boot on NVSwitch machines. Fix: run `systemctl enable` with its own error message, separate from the condition.

**10. Low — demo "service account" test is narrower than the claim.**
`tests/attack-demo.sh:103`: only `O_RDONLY`/`O_WRONLY` are tried (not `O_RDWR`), for 4 seconds, only while `nvidia-smi -L` runs. A pass doesn't exercise the write-recreation path the lock exists for (e.g. a real CUDA run that makes NVIDIA's library touch the UVM nodes). Fix: add `os.O_RDWR` and, if feasible, run a tiny CUDA binary instead of `nvidia-smi -L`.

**11. Low — demo Jupyter check may false-FAIL on non-200 tunnel responses.**
`tests/attack-demo.sh:44` requires exactly HTTP 200 from `/api`; if JupyterLab answers 302/403 (auth redirect) the tunnel check reports FAIL though the stack is fine. Fix: accept any HTTP response (`%{http_code}` ≥ 200 and < 500) as "reachable through the tunnel".

**No issue found** in: the mountinfo awk parsing (fields 5/6 are correct; the optional `shared:`/`master:` fields sit after field 7 and don't shift them; `/dev/nvidia*` names can't contain the escaped-space forms), the UVM major/`printf %x` comparison, the UVM minor assignment, the `nvidia-persistenced` SupplementaryGroups reasoning, mount propagation into Docker containers from the host-side service (the service runs in the host namespace; container `/dev` is a private tmpfs), or shutdown ordering (nothing needs to unmount at shutdown).
