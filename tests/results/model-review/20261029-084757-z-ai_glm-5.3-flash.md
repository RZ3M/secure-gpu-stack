# z-ai/glm-5.3-flash

**1. High — Multi-user notebook-to-notebook attacks are misjudged as covered.** The doc claims "Notebooks can't see other users' processes" (line 26) and the sandbox "protects the machine and other users" (line 41), but the known gap at line 61–63 admits one localhost TCP port per kernel remains. On a shared machine, another user can port-scan localhost and reach that port; the doc asserts the random key blocks it, but the port also reveals kernel existence and the key is in the kernel's process environment/filesystem, readable by same-user code only — fine — yet the doc never addresses **shared /tmp and /dev/shm** (line 31 list omits them): PyTorch/TensorFlow use `/dev/shm` for shared memory and temp files there; another local user reading leftover tensors, or a symlink attack in shared `/tmp`, leaks training data. Mitigation: per-user `/dev/shm` (tmpfs namespaced or `private` tmpfs in the sandbox), private `/tmp`, and a documented cleanup-on-exit for shm segments.

**2. High — Credential exfiltration from the user account is acknowledged but not mitigated where it's cheap.** Lines 39–42 concede notebook code can read HF/W&B tokens and "send them out," and line 43 defers outbound restriction to v0.2. For the primary threat named in the doc (malicious model/package, line 25), token theft is the *most likely* outcome and the stack could mitigate now: store tokens in a keyring/file readable only by a thin wrapper, or at minimum document `HF_TOKEN`-free shells for notebook runs. As written, the "supply chain" row (line 25) reads stronger than reality: modelscan + hash-locked wheels don't stop a clean-looking package from reading `~/.cache/huggingface/token`.

**3. High — Cloud metadata service (169.254.169.254) is absent.** Lambda and other clouds expose instance metadata/IMDS reachable from any process, including notebooks and containers. A malicious package (line 25 scenario) can fetch instance credentials or user-data (which often contains setup scripts/secrets). The firewall row (line 24) only covers *incoming* traffic. Mitigation: block or IMDSv2-style hop-limit enforcement, or at least document it; containers especially should not reach metadata.

**4. Medium — SSH agent forwarding is listed as a gap but is trivially fixable.** Line 52–53 says `ssh -A` is "still allowed." A hardening stack that already edits sshd (keys only, no root, no X11) can set `AllowAgentForwarding no` in sshd_config. Leaving a known, one-line mitigation open while listing it as "doesn't protect" is a claim-vs-delivery mismatch.

**5. Medium — GPU-specific leftovers: CUDA caches, core dumps, swap.** The "worth protecting" list (lines 9–18) and the gaps list never mention: core dumps (which can contain token strings from crashed processes), swap holding model weights/tokens after a job, and `~/.cache/torch`/`~/.triton` caches. Mitigation: `coredump` disabled or piped to a restricted handler, encrypted or no swap, and a documented `sgs-clean` for GPU caches. Also `LD_PRELOAD`/`PYTHONPATH`/`LD_LIBRARY_PATH` from user-writable dirs: the doc's sandbox row (line 26) doesn't say whether the notebook sandbox scrubs these; if a user's shell exports `LD_LIBRARY_PATH` to a project dir and the sandbox inherits it, "malicious model" code loads a hostile `libcudart` shim. Mitigation: env scrubbing in the sandbox unit.

**6. Medium — Multi-node/NCCL and InfiniBand traffic is unexamined, not just "untested."** Line 64–66 defers NVLink/MIG/InfiniBand to a test plan, but the threat-model table has no row for **another node on the Lambda private network**. NCCL over IB/TCP listens on ports and trusts peers; a neighbor rented instance can connect. This is a realistic attacker ("someone on the internet" row only covers inbound from the internet, line 24). Mitigation: firewall the private interface too, or document NCCL socket restrictions; at minimum add the row now rather than after testing.

**7. Medium — MIG is deferred, but the GPU row (line 15–16) implies device-file locking covers "the GPU."** On MIG-capable hardware (A100/H100 — exactly what Lambda rents), the `video`-group lock on `/dev/nvidia*` doesn't partition anything; a user with GPU access can reconfigure MIG instances if the management device (`/dev/nvidia-cap`/`nvidia-mig` nodes) isn't restricted. The doc should not imply GPU protection generally until MIG device handling is specified.

**8. Medium — "torch.load refuses code by default" overstates.** Line 25: PyTorch's default `weights_only=True` is recent and many workflows pass `weights_only=False` or use formats (`.pt` via `torch.jit`, pickle-based `datasets` cache, `np.load(allow_pickle=True)`) that still execute code. modelscan helps but has known bypass classes. The claim should be scoped ("refuses code in the stack's default loader paths"), and the mitigation list should mention that user venvs (line 58) get none of it.

**9. Low/Medium — "sgs-check is only useful if it can't be quietly fooled" (line 17–18) vs. root can make it lie (line 36–37).** The doc admits root defeats it, but the daily-run/login-message design (line 29) means a root-level compromise can *display* PASS while the machine is backdoored. Worth stating explicitly that the login banner is attacker-controllable post-root, so operators shouldn't treat a PASS banner as evidence — or ship a remote attestation option (e.g., push sgs-check output off-box).

**10. Low — "Docker publishes ports to localhost only" (line 24) is weaker than it sounds on multi-user machines.** A localhost-published port is reachable by *every local user*, including the notebook sandbox and other tenants. If a teammate publishes a service on 127.0.0.1, another user's notebook can reach it. Mitigation: per-user network namespaces for containers, or at least document this in the container row.

**11. Low — systemd user units and cron are unmentioned.** Line 26 covers kernel persistence plants, but the threat model never says whether the notebook sandbox blocks `systemctl --user` / `crontab` persistence by the *user's own* malicious code (the line 39–42 scenario). If the sandbox unit doesn't restrict `systemd-run --user`, a malicious package gains persistence that survives notebook restarts. Verify and state it.

**12. Low — "wheels only (no build scripts)" (line 25) doesn't cover malicious wheels.** A wheel's `*.data` entries and entry-point hooks execute on install/import without build scripts. pip-audit catches known CVEs, not malicious new packages. The claim should be softened or paired with an allowlist/quarantine for first-time installs in the stack env.

No issue: the "Root" and "Lambda's side" sections (lines 33–37, 49–50) are honest and correctly scoped; the io_uring/userns/BPF hardening row is appropriately specific.
