# z-ai/glm-5.3-flash

## Round C findings — delivery path, profile, pins, Python policy, tests

**1. Medium — Release has no cryptographic signature; the "published checksum" is only as trustworthy as the channel it's published on.**
`scripts/release.sh:24` emits a bare `SHA256SUMS`; nothing signs it, and `cloud-init/lambda-user-data.yaml:16-17` has the user paste `SGS_URL` and `SGS_SHA256` from (per the header) "a published release" — i.e., typically the same page. Scenario: the release page/host is compromised or a MITM on the user's copy step serves an attacker's tarball with a matching attacker hash; the cloud-init check at line 27 passes and root runs the attacker's `install.sh`. README:34 claims this "replaces Lambda Stack's unverified `wget | sh`", but checksum-only verification with no signature and no rollback protection is a weak version of that claim. Fix: minisign/GPG-sign `SHA256SUMS` with a key fingerprint published out-of-band, and have cloud-init verify the signature, not just the hash.

**2. Medium — The NCCL pin is version-only and origin-less, so it blocks Ubuntu security updates for libnccl2 and can be satisfied by any repository.**
`files/apt-pin-nccl:5-7` pins `version *+cuda13.0` at priority 600 with no `origin`/`release` qualifier. Ubuntu's own libnccl2 (no `+cuda13.0` suffix) sits at 500, so once the NVIDIA repo is configured, Ubuntu security updates for NCCL never win — contradicting README:36's "security fixes flow through Ubuntu" for the NVIDIA components. Worse, any other source (a PPA, a mirror) shipping a `*+cuda13.0` version also gets 600. Fix: `Pin: origin developer.download.nvidia.com` plus the version glob, or drop the pin and rely on the CUDA-repo's normal priority.

**3. Medium — TensorFlow's CUDA 12 libraries are installed from version ranges with no lockfile, contradicting criterion 7 ("hash-verified wheels only").**
`python/tf-cuda12.in:6-16` is all `>=x,<y` ranges; README:103 lists lockfiles only for `requirements.in` ("lock-*.txt … generated from this"), and no `lock-tf-cuda12*` exists in the tree. Scenario: a compromised or maliciously updated `nvidia-cudnn-cu12` wheel in range is installed unverified into `/opt/sgs/tf-cuda12` and preloaded for TensorFlow (per the file's own header). Unverified: whether `install.sh` generates a lock for this file at install time. Fix: hash-lock `tf-cuda12.in` like the main requirements, or pin exact versions with hashes.

**4. Medium — `attack-demo.sh` can leave a deliberately public container running on the target.**
`tests/attack-demo.sh:43-49`: the setup block starts `sgs-demo-public` bound to `0.0.0.0:8081` (line 47). If any step in the `&&` chain fails, line 49 does `exit 1`, skipping the cleanup at line 61; the cleanup ssh at line 61 can also fail (transient network) with no retry. Scenario: demo run against a Lambda instance, `docker network create` fails after the public container started → an intentionally internet-exposed port 8081 is left running indefinitely. Fix: trap/`always`-cleanup (run cleanup even on failure, with retries), and start the public container last.

**5. Medium — The network tests report PASS for any connection failure, not just for the intended security property.**
`tests/attack-demo.sh:22` `reachable()` treats any curl failure as "blocked": lines 25, 51, 53 pass when the host is down, a security group drops everything, or DNS fails — not because Jupyter/Docker are actually bound to localhost. Lines 35 and 38: `ssh root@…` and the password-auth probe "pass" whenever SSH is unreachable for any reason. Similarly `tests/user-checks.sh:45-47`: `hostname -I | awk '{print $1}'` may return a Docker bridge address or nothing (IPv6-only, no address), making the "doesn't answer on the network address" check vacuous. Fix: first assert positive connectivity (e.g., SSH works, then check the specific port is closed via `nc -z` from outside), and in user-checks pick the default-route address explicitly.

**6. Medium — "Malicious model files are caught" is detection-only; nothing in the stack prevents loading a malicious pickle, and the test never loads the `.pkl`.**
`tests/user-checks.sh:49-71` proves modelscan *flags* `model.pkl` (line 63) and that `torch.load` defaults to `weights_only` (line 69), but the pickle payload is never loaded, and no mechanism stops a researcher from running `pickle.load` / `torch.load(..., weights_only=False)` / loading a `.keras` file. README:49's table and the test's banner ("Malicious model files are caught") imply protection that doesn't exist for the most common ML formats. Scenario: a downloaded "checkpoint.pkl" with a `__reduce__` payload — modelscan prints a warning the user ignores, then the notebook loads it and runs arbitrary code. Fix: reword the claim, and consider a wrapper/hook that warns-or-blocks pickle-based loads by default (e.g., a sitecustomize guard the user must explicitly override).

**7. Medium — The documented user workflow (`sgs-venv` + `pip install`) has no hash pinning and no index pinning, so criterion 7 doesn't hold where users actually work.**
`bin/sgs-venv:34-38` gives users a pip that installs from whatever index `PIP_INDEX_URL`/config says, with no `--require-hashes`. README:24 claims "Python installs are hash-verified wheels only", but that's only true for the read-only stack env; every user environment — where flash-attn, transformers-from-git, etc. get installed — is unprotected against typosquatting and malicious wheels (including ones with build scripts, which criterion 7 says are never run). Fix: ship a pip.conf in the venv template pinning the index and `--require-hashes` for a curated allowlist, or at minimum document that user envs are unverified.

**8. Medium/Low — `sgs-venv` creates the `.pth` hook and pip wrappers *after* the hardening `chmod`, under the caller's umask.**
`bin/sgs-venv:28` runs `chmod -R go-w`, then lines 32 and 35-37 create `sgs-stack.pth` and `bin/pip`/`bin/pip3` with the ambient umask. Scenario: a user with umask 000 (or a permissive default on multi-user lab machines) creates an env; `sgs-stack.pth` is world-writable, and `.pth` files execute code on *every* interpreter start — another local user writes one line into it and gets code execution in the victim's Python. Fix: `umask 077` at the top of sgs-venv, or re-run `chmod -R go-w` after creating all files.

**9. Low — cloud-init extracts the tarball as root without `--no-same-owner`.**
`cloud-init/lambda-user-data.yaml:28` runs `tar -xzf` as root; GNU tar as root preserves archive ownership, so the tree is owned by the build machine's uid (typically 1000). The 0700 `mktemp -d` workdir (line 25) contains the exposure at extraction time, but if `install.sh` copies the tree into system paths preserving ownership (unverified — install.sh was reviewed in an earlier round), stack files end up owned by the target's uid-1000 user (`ubuntu` on Lambda), i.e., writable by the unprivileged account the stack is supposed to constrain. Fix: `tar -xzf --no-same-owner --numeric-owner`.

**10. Low — The "pip install into the stack is refused" test passes for the wrong reason.**
`tests/user-checks.sh:28-32`: any pip failure — PyPI unreachable, DNS failure, a proxy error — increments no failure and prints "pip install into the stack is refused (it's read-only)". Scenario: run the checks on an offline machine; the read-only guarantee is "verified" without pip ever reaching the venv. Fix: assert the specific failure (e.g., pip's "externally-managed/permission" error text, or pre-seed a local wheel and confirm the target path is untouched).

**11. Low — README's Jupyter claim ("requires its token on every endpoint") conflicts with the test, which expects HTTP 200 with no token.**
`tests/user-checks.sh:43-44` asserts `http://127.0.0.1:8888/api` returns 200 from an unauthenticated curl, while README:38 says the token is required "on every endpoint". Either `/api` is unauthenticated (and the README overclaims) or the test is wrong and would fail on a correctly configured machine. Fix: test an actual authenticated endpoint (expect 403 without token, 200 with it) and align the README.

**12. Low — README criterion 3 ("zero known vulnerabilities in the Python stack") is backed only by pip-audit over PyPI packages.**
README:20,51 counts advisories in the 149 pip packages; the far larger attack surface actually shipped — the NVIDIA driver, CUDA, cuDNN, NCCL, the Container Toolkit, Jupyter's Node/npm assets — has no vulnerability check in `sgs-check` per anything shown. A researcher loading an untrusted model file exercises cuDNN/CUDA parsers that pip-audit never sees. Fix: scope the claim to "PyPI packages", or add a system-package CVE check (e.g., against Ubuntu OVAL + NVIDIA advisories) to sgs-check.
