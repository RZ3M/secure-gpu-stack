# deepseek/deepseek-v4.1-flash-1017

1. **High — `sgs-check-sandbox.sh:7`**: `case "$level" in *SAFE*|*OK*)` matches the substring `SAFE` inside `UNSAFE`, so a badly weakened unit is reported OK. `systemd-analyze security` prints e.g. `9.6 UNSAFE 😨`; `$level` becomes `9.6 UNSAFE`; the glob reports “sandbox is in place”. Fix: match exact `OK`/numeric score, e.g. parse the number and `bad` if > 3.0; never use `*SAFE*`.

2. **High — `sgs-jupyter@.service:29-33`**: the sandbox does not hide `/var/run/docker.sock`; if the Jupyter user is in the `docker` group, notebook code can start a privileged container and become root on the host, despite the comment that it cannot root via sudo/setuid. Scenario: malicious package runs `docker run --rm -v /:/host --privileged ...`. Fix: do not put the Jupyter user in `docker`; use rootless Docker, or add `InaccessiblePaths=/var/run/docker.sock /run/docker.sock` to the unit (this breaks Docker CLI from notebooks) and run Jupyter as a separate non-docker user.

3. **High — `sgs-check-containers.sh:7,11`**: the check only regexes `Mounts.Source` for `docker.sock`; `-v /:/host`, `-v /var/run:/hostrun`, or `-v /etc:/etc` are not flagged. Docker’s root in the container has `DAC_OVERRIDE`, so a rw bind of `/` lets it write host files. Scenario: `docker run -v /:/host ... sh -c 'echo key >> /host/root/.ssh/authorized_keys'` passes the check. Fix: inspect both `.Mounts.Source` and `.Destination`; flag `/`, `/etc`, `/root`, `/home`, `/var/run`, `/run`, `/proc`, `/sys`, and rw bind mounts of those.

4. **High — `sgs-check-containers.sh:7`**: the inspect format omits `.HostConfig.Devices` and `.HostConfig.IpcMode`; `--device=/dev/sda` or `--ipc=host` is not flagged. A container root with `/dev/sda` can read the host disk; host IPC exposes host shared memory. Fix: include both fields and flag block devices, `/dev/mem`, `/dev/kmem`, `/dev/port`, and `IpcMode=host`.

5. **Medium — `sgs-check-containers.sh:7`**: the check omits `.HostConfig.SecurityOpt` and `.UsernsMode`; `--security-opt seccomp=unconfined`, `apparmor=unconfined`, and `--userns=host` are not flagged. Scenario: a container disables seccomp/AppArmor and exploits a kernel bug; or, with userns-remap configured, `--userns=host` maps container root to host root. Fix: inspect and warn/bad on these.

6. **Medium — `sgs-check-containers.sh:4`**: the comment says host networking is safe because “the firewall still filters it,” but the code does not inspect `.HostConfig.NetworkMode`; a `--net=host` container can reach `127.0.0.1` services and cloud metadata at `169.254.169.254`, which host firewalls commonly do not filter. Scenario: malicious image runs `curl http://169.254.169.254/latest/meta-data/iam/security-credentials/`. Fix: flag `NetworkMode=host` (warn, since multi-node NCCL may need it) or require explicit opt-in.

7. **Medium — `sgs-jupyter@.service:58,61-69`**: `RestrictAddressFamilies` lacks `AF_IB`, and `DeviceAllow` lacks `/dev/infiniband`. Multi-node NCCL over InfiniBand/RDMA will fail to open `/dev/infiniband/uverbs*`/`rdma_cm` or will fall back to TCP. Fix: add `DeviceAllow=/dev/infiniband/* rw` (or the `char-infiniband` group) and `AF_IB` if RDMA CM uses it; test with `NCCL_IB_DISABLE=0`.

8. **Medium — `sgs-jupyter@.service:33,56,61-69`**: FUSE mounts are broken three ways: `@mount` denies `mount`/`umount`, `/dev/fuse` is not in `DeviceAllow`, and `NoNewPrivileges=yes` prevents setuid `fusermount3` from elevating. Scenario: a notebook runs `gcsfuse`/`s3fs` to mount a dataset and gets “mount failed: Operation not permitted”. Fix: do FUSE mounts on the host, or add a documented drop-in that allows `/dev/fuse` and the needed mount syscalls.

9. **Medium — `sgs_cuda_preload.py:96`**: JAX defaults to CPU whenever `/proc/driver/nvidia/version` is absent, even if GPU device nodes are present or the Jupyter service starts before the nvidia module; the long-lived process never rechecks. Scenario: a GPU container without that proc mount, or boot-order Jupyter before nvidia loads, makes `jax.devices()` return CPU despite a usable GPU. Fix: also require absence of `/dev/nvidiactl` and `/dev/nvidia0`; avoid setting this permanently in a long-lived service, or defer JAX platform selection. (Container proc-mount behavior unverified here.)

10. **Medium — `sgs-check-containers.sh:6`**: `docker ps`/`docker inspect` stderr and exit status are discarded; if the daemon is down, permission is denied, or the timeout fires, `risky` is empty and the check emits neither `bad` nor `skip`. Scenario: `sgs-check` run without docker-group access prints no container finding, and the user assumes no risky containers. Fix: capture status and emit `skip`/`bad` when Docker is installed but unqueryable.

11. **Medium — `sgs-check-sandbox.sh:5-9`**: the score-only check catches weakening but not drop-ins that improve the score while breaking the required omissions. A drop-in with `MemoryDenyWriteExecute=yes` or `RemoveIPC=yes` raises the score, so `sgs-check` says OK, but JIT (`torch.compile`, numba, JAX) or `/dev/shm` DataLoader workers break. Fix: explicitly assert those directives are absent/off, and optionally compare the full `systemd-analyze security` output rather than only the aggregate score.

12. **Low/Medium — `sgs-check-ssh.sh:5,19`**: `sshd -T` without `-C` does not evaluate `Match` blocks, so a `Match User alice` + `X11Forwarding yes` is not seen; the check prints the global `x11forwarding no` and passes. Scenario: `/etc/ssh/sshd_config.d/00-x11.conf` is read before `10-sgs.conf` and sets `X11Forwarding yes` for alice; first-value-wins makes it effective, `sshd -T` still says `no`, and `sgs-check` reports OK. Fix: run `sshd -T -C user=<each account>,host=localhost,addr=127.0.0.1` for all accounts, or parse `Match` blocks.
