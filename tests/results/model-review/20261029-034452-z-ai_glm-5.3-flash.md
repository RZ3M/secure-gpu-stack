# z-ai/glm-5.3-flash

## Round D findings

**1. High — `sgs-sbom --output` follows symlinks; root-run SBOM write is a symlink-attack target**
`bin/sgs-sbom:142` opens the output with `os.O_WRONLY | os.O_CREAT | os.O_TRUNC` — no `O_NOFOLLOW`, no `O_EXCL`, fixed mode `0o644`. The tool runs as root during install. Scenario: the installer (or an operator) is told to write the SBOM into a directory a local user can write (`/tmp`, a user's home, a shared scratch dir); the user pre-creates `/tmp/sgs.cdx.json` as a symlink to `/etc/sudoers` or any root file → root truncates/overwrites it with attacker-influenced timing, or pre-stages content. Fix: `os.open(..., os.O_WRONLY | os.O_CREAT | os.O_TRUNC | os.O_NOFOLLOW, 0o644)` plus refusing to write into world/group-writable directories (check `os.stat(...).st_mode & 0o022` on the parent).

**2. High — the "RECORD hash" attests nothing: a malicious package can rewrite its own RECORD**
`bin/sgs-sbom:70-77` hashes the wheel's `RECORD` file and presents it as evidence the install is intact (comment at lines 71-72: "changes if any of them do"). But `RECORD` lives inside the same attacker-writable `.dist-info` directory as `METADATA`. Scenario: a malicious pip package ships code that, at install or first import, patches `site-packages/torch/nn/module.py` and updates `torch-*.dist-info/RECORD` so its self-hash matches the pristine build. `sgs-check`/SBOM consumers comparing the recorded hash against a known-good value get PASS while the code is backdoored. Fix: recompute hashes of the files *listed in* RECORD (as `pip check`/`--require-hashes` tooling does) and hash that result, or at minimum mark the property `sgs:hash-of` as untrusted self-attestation.

**3. Medium — component name/version taken verbatim from attacker-controlled METADATA; purl impersonation and malformed purls**
`bin/sgs-sbom:61-66` reads `Name:`/`Version:` from `METADATA` with no validation and no cross-check against the trustworthy `.dist-info` directory name, then builds `pkg:pypi/{name.lower().replace('_','-')}@{version}` (line 96) unescaped. Scenario: a malicious package ships `METADATA` with `Name: torch` (or `Name: ../../evil`, `Version: 1.0 (payload url=https://...)`) — the SBOM then misdescribes the machine: a vulnerability scanner matches the wrong component, and the purl contains characters illegal in the purl spec, breaking downstream parsers. Fix: derive name/version from the `*.dist-info` directory name (which pip itself keys on) and use METADATA only as a fallback; reject/escape purl-unsafe characters.

**4. Medium — held dpkg packages are silently omitted from the SBOM**
`bin/sgs-sbom:39` keeps only lines whose `db:Status-Abbrev` starts with `ii`. A held package has want-status `h` (abbrev `hi `), so an installed-but-held package — exactly the kind an admin pins because it's known-broken or known-vulnerable — is missing from the SBOM (unverified: exact abbrev formatting per dpkg version). Scenario: attacker gets a vulnerable package version held in place; `sgs-check`/SBOM reports the machine clean. Fix: test the middle two status chars (`it` = installed) rather than the want letter, e.g. `status[1:3] == "it"`.

**5. Medium — `awk -v` mangles the filename before matching SHA256SUMS**
`cloud-init/lambda-user-data.yaml:45`: `awk -v f="${SGS_URL##*/}" ...` — awk processes escape sequences in `-v` assignments, so a URL filename containing `\` (e.g. a path like `releases\0.1.0/sgs.tar.gz`) is corrupted before matching. This is fail-closed today (mismatch → exit 1), but combined with a SHA256SUMS containing multiple entries it means the *wrong* line can never be selected — the real risk is the inverse: if a future SHA256SUMS lists `dir/sgs.tar.gz` and the URL is bare, `$2 == f` fails and install aborts. Fix: pass the filename via `ENVIRON` (`f=...` env var, `awk -v` removed) or match with `grep -F " $f"` and take field 1.

**6. Low — `echo` for the allowed_signers file can inject signer lines**
`cloud-init/lambda-user-data.yaml:40`: `echo "$SGS_ALLOWED_SIGNER" > "$work/allowed_signers"`. The YAML block scalar makes multi-line pastes easy; any embedded newline becomes an additional allowed_signers line, and `ssh-keygen -Y verify` will accept *any* principal/key on those lines that matches `-I release@secure-gpu-stack`. Scenario: user pastes the signer line with a trailing wrapped key fragment; a second line beginning `release@secure-gpu-stack ssh-ed25519 AAAA…` (attacker key from a phishing "setup guide") is silently honored and the attacker's tarball verifies. Fix: `printf '%s\n' "$SGS_ALLOWED_SIGNER"` plus a guard rejecting values containing newlines, and/or `grep -c . allowed_signers` must equal 1.

**7. Low — duplicate `bom-ref`s when a package has both egg-info and dist-info**
`bin/sgs-sbom:85` globs both `*.dist-info` and `*.egg-info` in the same site dir; a package installed with both (common for mixed pip/setup.py installs) yields two components with identical purl and identical `sgs:environment`, hence identical `bom-ref` (lines 115-116), violating CycloneDX's bom-ref uniqueness and confusing consumers. Fix: dedupe on bom-ref, or append the dist-info basename to the ref.

**8. Low — `shasum` may not exist on the Ubuntu build host**
`scripts/release.sh:27` uses `shasum -a 256`. Ubuntu 24.04 ships `sha256sum`; `shasum` is only present with Perl installed. On a fresh build container the release aborts after the tarball is built but before `SHA256SUMS` exists — and because line 38's signing block never runs, a previously published `SHA256SUMS.sig` in `dist/` (only removed at line 39 *inside* the `if`) goes stale relative to the new tarball. Fix: prefer `sha256sum` with a `shasum` fallback, and `rm -f SHA256SUMS.sig` unconditionally before line 27.

**Non-findings checked:** the `-I`/`-n` identity and namespace are hardcoded on both sides (release.sh:40, yaml:42-43), so namespace confusion is closed; `curl --proto-redir '=https'` blocks downgrade redirects; `mktemp -d` (0700, root) closes the fetch→verify→extract TOCTOU window; `curl -f` + explicit `|| exit 1` on both checks means no plausible shell-parsing path skips a check; the unsigned path with `SGS_SHA256=REPLACE-ME` left in place fails `sha256sum -c` rather than installing.
