# deepseek/deepseek-v4.1-flash-1017

Ranked findings:

1. **High — MIG/nvidia-caps device nodes are outside both the restriction and the check.** `files/sgs-gpu-devices:22` only globs `/dev/nvidia*` at depth 1; `files/sgs-check-driver-block.sh:23` uses `find /dev -maxdepth 1`; `files/72-sgs-nvidia-devices.rules:4-5` only fires on driver/module add. Defect: `/dev/nvidia-caps/nvidia-cap*` char devices are never chgrp/chmod’ed or checked, and creating a MIG instance triggers neither udev rule nor the UVM path unit. Scenario: on an H100 with MIG, `nvidia-smi mig -cgi ...` creates `/dev/nvidia-caps/nvidia-cap1` 0666; a non-video user opens it, and `sgs-check` reports PASS because its `find` never sees it. Fix: recurse into `/dev/nvidia-caps/*` in `sgs-gpu-devices` and `sgs-check`, and add a udev rule for `KERNEL=="nvidia-cap*"` or a path watch on `/dev/nvidia-caps`.

2. **High — `sgs-check` never stats the actual device files, so a 0660 root:users or uid-1000-owned device passes.** `files/sgs-check-driver-block.sh:23-35` only checks for other read/write bits and compares `/proc` `DeviceFileGID` to video; it never verifies the real uid/gid/mode of `/dev/nvidia*`. Defect: a device file that is `0660 root:users` (or owned by uid 1000) is not world-accessible, so `open_devs` is empty, `dmode`/`dgid` match, and the check prints “GPU device files are for the video group only.” Scenario: an admin or another tool runs `chgrp users /dev/nvidia0`; every local user in `users` can open the driver, but `sgs-check` PASSes. Fix: for each char device, `stat -c '%u %g %a'` and require uid 0, gid video, mode 0660 (or at least group video and no other bits); also check `DeviceFileUID: 0` in `/proc/driver/nvidia/params`.

3. **High — `sgs-check` treats an active path unit as proof the UVM fix works, even if the service is failing or the unit is disabled for next boot.** `files/sgs-check-driver-block.sh:32-35` only runs `systemctl is-active --quiet sgs-gpu-devices.path`. Defect: an active path unit can have a failing `sgs-gpu-devices.service`, and it can be active but not enabled. Scenario: `/usr/local/sbin/sgs-gpu-devices` is deleted or made non-executable; the path unit stays active, current UVM is 0660, and `sgs-check` PASSes. The next root CUDA run recreates UVM 0666, the path triggers the broken service, and UVM stays 0666. Fix: check `systemctl is-enabled --quiet sgs-gpu-devices.path` and `systemctl show -p Result --value sgs-gpu-devices.service`, or run the script and re-stat the UVM files.

4. **High/Medium — `nvidia-cdi-refresh`’s `ExecStartPost` is skipped if `nvidia-ctk` fails after creating some nodes.** `files/nvidia-cdi-refresh-sgs.conf:6` uses `ExecStartPost=+...`. Defect: systemd does not run `ExecStartPost` when the main `ExecStart` fails, so a partial `nvidia-ctk system create-device-nodes` can leave 0666 nodes behind. Scenario: `nvidia-cdi-refresh` creates `/dev/nvidiactl` 0666, then fails before creating `/dev/nvidia-uvm`; `ExecStartPost` never runs, there is no udev add event for the `mknod`, and the path unit only watches UVM, so `/dev/nvidiactl` stays 0666. Fix: use `ExecStopPost=+/usr/local/sbin/sgs-gpu-devices` (runs regardless of success) in addition to or instead of `ExecStartPost`.

5. **Medium/High — the path unit only watches UVM, so 0666 recreations of `nvidiactl`/`nvidia0` that do not touch UVM are never corrected.** `files/sgs-gpu-devices.path:9-11` watches only `/dev/nvidia-uvm` and `/dev/nvidia-uvm-tools`. Defect: any path that recreates `/dev/nvidiactl` or `/dev/nvidia0` 0666 without changing UVM leaves them open. Scenario: the module options are not active (`install_driver.sh:54-55` sets `NEED_REBOOT=1` but does not enforce a reboot); root runs an NVML-only program that recreates `/dev/nvidiactl` and `/dev/nvidia0` 0666 but not UVM; no udev add event and no path trigger, so a non-video user can open them. Fix: add `PathChanged=/dev/nvidiactl` and `PathChanged=/dev/nvidia0`, or use a single inotify watcher on `/dev` for `nvidia*`; also run `sgs-gpu-devices` after any root GPU use until reboot.

6. **Medium/High — the mode filter is both too narrow and too broad.** `files/sgs-gpu-devices:22-26` skips any file whose other bits are 0/1, even when a non-video group has access, and it chgrps/chmods every world-accessible `/dev/nvidia*` char device to video 0660, including NVSwitch control nodes. Defect: `0640 root:users` is left readable by `users`, while `0664 root:root` `/dev/nvidia-nvswitchctl` becomes video-writable. Scenario: (a) `/dev/nvidia0` is `0640 root:users`; the script sees last digit 0 and skips; `sgs-check` sees no other bits and PASSes; non-video users in `users` can read the driver. (b) `/dev/nvidia-nvswitchctl` is `0664 root:root`; the script chgrps it to video and chmods 0660, giving video users write access to NVSwitch/Fabric Manager control they did not have before. Fix: distinguish compute nodes (`nvidiactl`, `nvidia[0-9]*`, `nvidia-uvm*`) from control nodes (`nvidia-nvswitch*`, `nvidia-caps`); for compute nodes always enforce root:video 0660, and leave NVSwitch root-only or use a dedicated group.

7. **Medium — the path unit keeps the default trigger limit while the service disables its own start limit, so a local video user can trip the path unit into failed state or cause a fork storm.** `files/sgs-gpu-devices.path:9-11` has no `TriggerLimitIntervalSec=0`; `files/sgs-gpu-devices.service:7` sets `StartLimitIntervalSec=0`. Defect: rapid UVM changes start the service for every trigger until the path unit’s default trigger limit is hit, after which the path unit fails and stops watching. Scenario: a video-group user runs many short CUDA processes; each recreates UVM 0666 and triggers the path. After the default burst, `sgs-gpu-devices.path` is failed; a later root CUDA run recreates UVM 0666 and nothing fixes it. Fix: set `TriggerLimitIntervalSec=0` or a high burst in the path unit, and use a coalescing long-running watcher instead of one service start per change; keep a service start limit to avoid fork storms.

8. **Medium — the attack demo tests only four device files, so multi-GPU and MIG misconfigurations pass.** `tests/attack-demo.sh:94-95` loops over only `/dev/nvidiactl`, `/dev/nvidia0`, `/dev/nvidia-uvm`, `/dev/nvidia-uvm-tools`. Defect: `/dev/nvidia1`…`/dev/nvidiaN` and `/dev/nvidia-caps/*` are never tested. Scenario: on a multi-GPU H100/B200 machine, a race leaves `/dev/nvidia1` 0666; the demo tests `nvidia0` only and prints PASS “a service account (nobody) can’t open the GPU’s device files.” Fix: iterate all `/dev/nvidia*` char devices, including `/dev/nvidia-caps/*`, and fail if any opens.

9. **Medium — the attack demo only tests read-write opens, so a world-readable device passes.** `tests/attack-demo.sh:95` uses `exec 3<>$d`, which requires read-write. Defect: a `0664` or `0644` device that a non-video user can open `O_RDONLY` is reported as not openable. Scenario: `/dev/nvidiactl` is `0664 root:video`; `nobody` can open it read-only and issue query ioctls, but `exec 3<>` fails with `EACCES`; the demo PASSes. Fix: test read and write separately as `nobody` (`test -r`, `test -w`, or `exec 3<` and `exec 3>`), and fail if either succeeds.

10. **Medium — the attack demo’s GPU test turns sudo/SSH failures into PASS or SKIP.** `tests/attack-demo.sh:92-99` ignores the exit status of `sudo nvidia-smi` and `sudo -u nobody`, and treats empty output as “no NVIDIA driver.” Defect: a sudo password prompt, a sudoers denial of `-u nobody`, or an SSH drop makes the test report success. Scenario: the `ubuntu` user has sudo but requires a password; `sudo nvidia-smi` and `sudo -u nobody` fail; `opened` becomes `checked`; the demo prints PASS. Or SSH drops during the test; `opened` is empty; the demo prints SKIP and the final “Nothing reachable that shouldn’t be.” Fix: run `sudo -n true` first and fail/skip explicitly if it fails; check the exit status of `on_host` and each `sudo`; distinguish “no `/dev/nvidiactl`” from “test failed.”

11. **Medium — the installer does not check that `sgs-gpu-devices.path` was enabled, and under `set -e` can abort before applying the restriction.** `install_driver.sh:76-77` runs `systemctl enable sgs-gpu-devices.path >/dev/null 2>&1` and `systemctl restart sgs-gpu-devices.path` unchecked; `install_driver.sh:85` runs the script only after them. Defect: if `enable` fails, the installer either aborts before line 85 (under `set -e`) or continues and reports success with the path unit disabled; if `restart` fails under `set -e`, line 85 never runs. Scenario: systemd is not fully available or the unit file is missing; the installer exits or reports success, current `/dev/nvidia*` may remain 0666, and after reboot the path unit is not enabled, so root CUDA leaves UVM 0666. Fix: run `/usr/local/sbin/sgs-gpu-devices` before the systemctl calls, and guard `enable`/`restart` with `|| info "WARNING..."` or a trap so the restriction is always applied and failures are reported.

12. **Medium — CDI specs can keep gid 44 after the installer changes the video gid.** `install_driver.sh:42` rewrites `NVreg_DeviceFileGID` when video is not gid 44, and `files/nvidia-cdi-refresh-sgs.conf:6` only chgrps/chmods after `nvidia-cdi-refresh`; it never regenerates the CDI spec. Defect: if `nvidia-ctk` records gid 44 in the CDI spec before `sgs-gpu-devices` chgrps the devices to the real video gid, containers get gid 44 while the device files are group 1000. Scenario: on a system where `video` is gid 1000, the installer sets `NVreg_DeviceFileGID=1000` and `sgs-gpu-devices` chgrps devices to 1000; a container using the stale CDI spec gets gid 44 and cannot open the 0660 group-1000 device files. Fix: after chgrp, run `nvidia-ctk cdi generate` (or restart `nvidia-cdi-refresh`) so the spec records the actual video gid, or configure the CDI spec to use the host video gid/additionalGids. (Unverified if `nvidia-ctk` re-reads the device gid or if `additionalGids` already includes 1000.)
