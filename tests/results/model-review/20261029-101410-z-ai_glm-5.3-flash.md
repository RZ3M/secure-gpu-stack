# z-ai/glm-5.3-flash

## Findings (most severe first)

**1. HIGH — `files/sgs-guard.nft:13` — root-owned containers on host networking read the metadata service.**
A container started with `docker run --network host` never traverses the `forward` chain; its packets appear on the `output` hook with `meta skuid 0` (container root = host root), so both reject rules are bypassed. A malicious image that mounts nothing still gets one unauthenticated HTTP GET: instance credentials / user data. Same gap in `bin/sgs-egress:82-87` ("Containers get no new outbound connections at all" — false for `--net=host` root containers, which match `meta skuid 0 accept` at line 73).
*Fix:* match the container's cgroup instead of relying on the forward hook, e.g. `socket cgroupv2 level 2 "machine.slice…"`, or document and enforce that host networking is refused for containers (drop-in `docker.service` with `--iptables` plus a check in sgs-check that fails if a running container has `NetworkMode=host`).

**2. HIGH — `sgs-check-startup.sh:12,28` — symlink swap and deletions are invisible: false PASS.**
Two compounding defects: (a) the rc/authorized_keys loop hashes only non-symlinks (`[ ! -L "$f" ]`), so `rm ~/.bashrc && ln -s /tmp/x/.bashrc` (or swapping `authorized_keys` for a symlink) makes the file *disappear* from `startup_files`; (b) `comm -13` reports only lines present in the new scan, not in the record, so removals are never flagged. Net effect: replacing any watched file with a symlink — or simply deleting a watched file (e.g. removing the recorded `authorized_keys` before adding a new one, then re-adding after check runs) — produces silence where a WARN is due.
*Fix:* run both `comm -13` and `comm -23` and report disappeared files; for symlinks, hash `readlink -f` and record the link itself (as the systemd/autostart loop at 14-15 already does) instead of skipping.

**3. HIGH — `sgs-check-startup.sh:5-16` — the watch list misses the standard user-manager persistence path, so planted persistence yields a clean PASS.**
`~/.local/share/systemd/user/` is the canonical location for user units (and what `systemctl --user enable` writes into via the link farm); only `~/.config/systemd/user` is watched (line 14). Also unwatched, all directly usable by a uid≥1000 attacker: `/etc/systemd/system` and `/etc/systemd/user` drop-ins, `/etc/profile.d/*`, `/etc/sudoers.d/*`, at jobs (`/var/spool/cron/atjobs`), `~/.ssh/rc` (executed by sshd before the shell), `~/.ssh/environment`, `~/.pam_environment`, `~/.config/environment.d/`, and Python startup injection (`~/.local/lib/python3.x/site-packages/*.pth`, `usercustomize.py`) — the last being the most likely vector for the "malicious pip package" adversary since any `python` invocation runs it, not just a login shell.
*Fix:* add those paths to `startup_files`; for `.pth`/sitecustomize, hash the whole user site-packages directory listing. Mark sgs-check output as "watched: cron, shell rc, user units, SSH keys" only after it's actually true — the current PASS message at line 30 overstates coverage ("No cron job, shell startup file, user service … changed") when the service coverage is half the real directory.

**4. MEDIUM — `sgs-check-startup.sh` silently degrades when not run as root: record is incomplete, later runs report PASS.**
Line 6 `sha256sum < "$f"` on an unreadable root-owned crontab fails the redirection, that file is skipped without any marker, and line 36 happily records a partial list. A later run as root compares a full scan against the partial record — the diff shows only *new* root files (which look like churn), and anything planted before the first root run is baseline-accepted. The script never checks EUID.
*Fix:* at the top, `[ "$(id -u)" = 0 ] || { echo "run as root"; exit 1; }` (matching `need_root` in `bin/sgs-egress:34`), and make `sha256sum` failures fatal (`set -o pipefail` / explicit check) rather than silent skips.

**5. MEDIUM — `files/sgs-guard.nft:13-14` — only AWS's two metadata addresses are covered; other clouds' metadata endpoints are open.**
Azure's WireServer `168.63.129.16` (serves IMDS-style data and is a trust boundary for host extensions) and ECS task metadata `169.254.170.2` are reachable by any user and any forwarded container. If the stack claims cloud-agnostic protection ("a cloud metadata service"), the claim is only true on AWS/GCP. Also, the file comment (line 2) and the sgs-check message hardcode 169.254.169.254, so a GCP/Lambda user is told the IPv6 guard exists but `sgs-check-metadata.sh` never tests `fd00:ec2::254` — the IPv6 rule could be broken (or the address wrong) with no check noticing.
*Fix:* add `168.63.129.16` and `169.254.170.2` (v4/v6 as applicable), and extend sgs-check to probe the IPv6 address as well (`curl -g 'http://[fd00:ec2::254]/'` as nobody).

**6. MEDIUM — `sgs-check-metadata.sh:5-6` — the check can be satisfied by a firewall other than the guard, and only tests one path.**
Exit 7 from curl is also produced by egress strict mode's reject (`bin/sgs-egress:80`) or any other local rule; the `nft list table inet sgs_guard` guard at line 6 only proves the table exists, not that it contains the reject rules (the file could have been replaced with an empty `table inet sgs_guard {}`, which lists fine). It also tests only host-namespace IPv4 output as uid `nobody` — the forward path and IPv6 path that the guard actually claims to protect (lines 14, 17-19) are never exercised.
*Fix:* grep the listed table for the two daddr/reject rules, and add a second probe through a container on the default bridge (metadata should be refused there too).

**7. MEDIUM — `bin/sgs-egress:85-86` — the container lockdown matches only `docker0` and `br-*` interface names.**
A user-defined Docker bridge with an explicit name (`docker network create --opt com.docker.network.bridge.name=egress0 mynet`), Podman's default `podman0`, or CNI-created bridges are neither matched by `iifname` nor blocked, and their new outbound connections flow under the *output* chain — where, if the container process is not root (rootful containers can run as `-u`), they're subject only to the user rules; a root process inside them gets full root-class access (line 73). Strict mode's "Containers get no new outbound connections at all" is interface-name-dependent.
*Fix:* invert the forward policy: `ct state new reject` by default and accept only named infra (or match on the cgroup of the container, as in finding 1).

**8. MEDIUM — `bin/sgs-egress:95-98` — DNS enforcement depends on the *global* resolved drop-in, which is one file away from being inert, and the status check never verifies it.**
`status` (lines 137-144) checks only whether the nft table exists; it never checks that `systemd-resolved` actually points at 127.0.0.2 or that `sgs-egress-dns.service` is running. If a later drop-in (higher lexical precedence in `resolved.conf.d`) overrides `DNS=`, or the DNS service dies, root and user lookups fall back to the OS default — the nft rules still block direct port-53 for non-root, but *root* silently regains unrestricted DNS and, more importantly, the "every lookup goes through the strict resolver" audit trail (lines 18-19) is false while the tool still reports strict mode on.
*Fix:* in `status`, assert `resolvectl dns | grep 127.0.0.2` and `systemctl is-active sgs-egress-dns.service`, and fail loudly otherwise.

**9. LOW/MEDIUM — `bin/sgs-egress:45` — upstream resolvers are snapshotted at `apply` time and never refreshed.**
The nameserver list is read from `/run/systemd/resolve/resolv.conf` once per `apply`. On a VM whose DHCP lease changes DNS (or which moves networks / attaches a VPN), dnsmasq keeps forwarding to the stale, now-wrong server: resolution of allowed domains breaks (deny-by-failure, so fail-closed — good) but also, if the old resolver IP is later reassigned, allowed-domain queries are sent to an attacker-controlled server that can return addresses which are then pinned into `allow4`/`allow6` and become connectable. Unverified whether any supported workflow actually rotates resolv.conf here; if not, downgrade.
*Fix:* have dnsmasq forward to the resolved stub path via `server=/d/127.0.0.53` won't loop with `Domains=~.` pointed back — instead re-run `apply` on a `resolv.conf` change (path unit) or use DoT/upstream IPs from the cloud provider's documented resolver.

**10. LOW — `files/sgs-guard.service:14` — a failed load at boot leaves the machine unprotected with no marker.**
If `nft -f` fails (module not yet loaded, parse error after a bad edit, nftables binary missing on a partially upgraded image), the unit fails but boot proceeds and networking starts; nothing persists an error and nothing at boot retries. The user's only signal is a later `sgs-check` run, which many will do days later. *Fix:* add `OnFailure=` (or a `ExecStartPost` that writes a state flag sgs-check keys off), and `ExecStartPre=/usr/sbin/modprobe nf_tables || true` — or at minimum have sgs-check distinguish "table missing" from "table present but rules wrong" (see finding 6).

**11. LOW — `bin/sgs-egress:110-115` — the self-test can be green while strict mode is broken, and can itself be a footgun.**
The success probe uses the *first* line of the allow list; if that entry is commented-adjacent garbage or a subdomain with no A record, dnsmasq returns no answer, curl times out, and the tool prints "NOT reachable" with a suggestion to check the journal — but the nft rules and resolver were applied successfully; conversely, if the user's own shell aliases curl or `runuser` is unavailable, the false "reachable" path for `example.com` (line 116-117) is the only real signal. Also unverified: whether `runuser -u nobody` can write the curl cookie/error path in `$HOME`-less contexts on all images. *Fix:* probe with `curl --resolve` against a pinned address, and treat any non-7 failure of the example.com probe distinctly from a refusal.

**12. LOW — `bin/sgs-egress:74` — the DNS-exempt rule is UID-based, and UID namespaces are unverified.**
`meta skuid $uid … dport 53 accept` trusts that any socket bound by kuid `sgs-egress` is dnsmasq. Anything else that obtains that uid (a second dnsmasq instance, or — unverified — a user namespace mapped to that uid) becomes an unrestricted UDP/TCP-53 egress path. Practical but low: fix by additionally matching the process's cgroup (`socket cgroupv2 "sgs-egress-dns.service"`) or the `inet` `meta mark` set by the service unit.

No issue found with the `set -u` handling in `bin/sgs-egress` (`${1:-status}` and the `local` declarations cover the uses), and no issue with the guard's same-priority interaction with other nft base chains (a reject in one base chain applies even if another chain accepts).
