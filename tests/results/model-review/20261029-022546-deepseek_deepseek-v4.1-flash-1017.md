# deepseek/deepseek-v4.1-flash-1017

1. **High – `sgs-check` executes an attacker-controlled `SGS_PIP_AUDIT` as root.** `bin/sgs-check:305` takes the path from the environment and `bin/sgs-check:313` runs it after the script has required root (`bin/sgs-check:24`). Scenario: a user allowed to run `sudo sgs-check` runs `sudo SGS_PIP_AUDIT=/tmp/evil sgs-check`; `/tmp/evil` runs as root. Fix: remove the env override, or require the path to be root-owned and not writable by the invoking user.

2. **High – audit rules watch directories, not the files inside them, and miss `/etc/apt/sources.list.d` and `/etc/apt/keyrings`.** `install.sh:540-548` adds `-w /etc/apt/`, `-w /etc/docker/`, `-w /etc/nvidia-container-runtime/`, etc. Audit directory watches are not recursive; they only catch create/delete/rename in the directory. Scenario: an attacker modifies `/etc/docker/daemon.json` or `/etc/nvidia-container-runtime/config.toml` in place, or adds a malicious source/key under `/etc/apt/sources.list.d/` or `/etc/apt/keyrings/`, and no `sgs-` audit record is produced. Fix: add explicit `-w` rules for each file and subdirectory, e.g. `/etc/apt/sources.list.d/`, `/etc/apt/keyrings/`, `/etc/docker/daemon.json`, `/etc/nvidia-container-runtime/config.toml`.

3. **Medium – Jupyter’s token is written to the systemd journal.** `files/sgs-jupyter@.service:14` starts JupyterLab without suppressing its startup URL, and systemd captures stdout/stderr to the journal. Scenario: another local user in `adm`/`systemd-journal` reads the token from the journal and connects to `127.0.0.1:8888` as the target user, who may have passwordless sudo. Fix: add `--ServerApp.log_level=WARN` (or `StandardOutput=null`) and keep the runtime token file 0600.

4. **Medium – `sgs-check`’s apt source check accepts `trusted=yes` and unknown third-party keys.** `bin/sgs-check:79-94` parses sources but never inspects `trusted`/`allow-insecure`/`allow-weak`; `bin/sgs-check:105-118` only checks HTTPS and that `signed-by` is present. Scenario: `deb [trusted=yes signed-by=/etc/apt/keyrings/evil.gpg] https://evil.example/repo` is reported PASS “HTTPS, key limited to this source”, even though apt will trust it without a valid signature. Fix: reject `trusted=yes`, `allow-insecure`, `allow-weak`; check the key file is root-owned and not writable; report unknown third-party sources as NOTE/WARN rather than PASS.

5. **Medium – `sgs-check` ignores a global apt key named `ubuntu-keyring-*`.** `bin/sgs-check:123` excludes `! -name 'ubuntu-keyring-*'`. Scenario: a malicious key installed as `/etc/apt/trusted.gpg.d/ubuntu-keyring-evil.gpg` is skipped, and `bin/sgs-check:125-129` reports “No third-party key is trusted for every repository”. Fix: exclude only the exact Ubuntu keyring filenames or verify fingerprints.

6. **Medium – `sgs-check`’s Docker `daemon.json` checks are simple greps that duplicate JSON keys can fool.** `bin/sgs-check:217-223` and `bin/sgs-check:230-242` grep for `"ip": "127.0.0.1"`, `"no-new-privileges": true`, etc. JSON parsers such as Go’s take the last duplicate key. Scenario: a `daemon.json` with the good `"ip": "127.0.0.1"` followed by `"ip": "0.0.0.0"` makes `sgs-check` PASS while Docker binds to all interfaces. Fix: parse `daemon.json` with Python and inspect the effective values.

7. **Medium – `sgs-check`’s apt pin check only flags priorities above 1000.** `bin/sgs-check:131-137` uses `n + 0 > 1000`. A pin at exactly 1000 still allows downgrades. Scenario: a pin `Pin-Priority: 1000` forces an older vulnerable package, but `sgs-check` reports “No apt pin can override Ubuntu’s updates or force downgrades”. Fix: flag `>= 1000`.

8. **Medium – `sgs-check`’s SSH check ignores `KbdInteractiveAuthentication`.** `bin/sgs-check:493-495` only checks `passwordauthentication` and `permitrootlogin`. Scenario: `PasswordAuthentication no` but `KbdInteractiveAuthentication yes` with PAM still accepts passwords, yet `sgs-check` reports “Password login is off”. Fix: also require `kbdinteractiveauthentication no`.

9. **Medium – `sgs-check`’s stack isolation check only verifies that the venv exists.** `bin/sgs-check:262-264` prints PASS “Stack lives in its own environment” for any `/opt/sgs/venv/bin/python`. Scenario: `pyvenv.cfg` has `include-system-site-packages = true` or a `.pth` adds `/usr/lib/python3/dist-packages`, so the stack imports Ubuntu’s packages, but `sgs-check` still PASSes. Fix: read `pyvenv.cfg` and verify `include-system-site-packages = false`; check for `.pth` files adding system paths.

10. **Medium – `sgs-check`’s integrity check ignores files not listed in any `RECORD`.** `bin/sgs-check:377-403` builds `claims` only from `*.dist-info/RECORD` and hashes those paths. Scenario: an attacker adds `sitecustomize.py` or `evil.pth` to site-packages; the integrity check reports “All N installed files match” and never notices the extra file. Fix: also walk the site-packages and flag files not in any `RECORD` (excluding `__pycache__`/`.pyc`).

11. **Medium – `sgs-check`’s CDI writability check misses owner-writable specs.** `bin/sgs-check:243-245` uses `find /etc/cdi /var/run/cdi -perm /022`, which only checks group/other write. Scenario: a CDI spec owned by a non-root user with mode 0644 is writable by that user, who can add host mounts or hooks to every GPU container, but `sgs-check` PASSes. Fix: check that the owner is root and that group/other write bits are clear, and check the directories too.

12. **Medium – the firewall allows all incoming traffic on `tailscale0`, not just SSH.** `install.sh:255-259` runs `ufw allow in on tailscale0`. Scenario: a user starts TensorBoard/Ray/a dev server on `0.0.0.0`; every device in the tailnet can reach it, because Tailscale’s default ACL allows all tailnet devices. Fix: allow only SSH on `tailscale0`, or specific ports, and document that users must add rules for other services.
