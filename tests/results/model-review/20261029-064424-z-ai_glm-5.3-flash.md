# z-ai/glm-5.3-flash

## Findings (most severe first)

**1. HIGH — aa-exec bypass check samples one profile and can report PASS on a bypassable machine**
`sgs-check-kernel-block.sh:19-21`. `grep -ls ... | head -1` picks a single file, and if that file has no top-level `profile` line (e.g. it's an abstraction/include that merely contains `userns,`), `prof` is empty and the aa-exec test is *skipped entirely* — line 23 then prints "even through aa-exec (tried …)"-style PASS with no aa-exec attempt at all. Even when a profile is found, if that one profile denies userns while another (e.g. `chrome`, or any unconfined profile — the actual Qualys path) allows it, you get a false PASS and the machine is still rootable via `aa-exec`.
*Scenario:* fresh install, first alphabetical match in `/etc/apparmor.d/*` containing `userns,` is a confined helper profile → `aa-exec -p $prof -- unshare -Ur` fails → PASS, while `aa-exec -p chrome -- unshare -Ur` gives uid 0.
*Fix:* loop over **all** files matching `userns,`, extract every profile name, and fail if *any* of them lets `nobody` reach `unshare -Ur`; also treat "no profile found" as a WARN, not a PASS.

**2. HIGH — dpkg --verify block passes on error, and excludes held packages**
`sgs-check-native-block.sh:15-17`. stderr is discarded and *any* empty stdout — including dpkg dying on a bad/unresolvable package name, a locked dpkg database, or a corrupted status file — is reported as "files match their packages". Additionally line 11's `awk '$1 ~ /^ii/'` drops packages whose Status-Abbrev is `hi` (installed but held — a plausible state on a machine where an admin pinned the driver), so held NVIDIA/CUDA packages are silently never verified.
*Fix:* capture stderr, check `dpkg --verify` exit status, treat non-zero as WARN; match `/^i[if]/` (or `^[ihr][cn]` minus `rc`) instead of `^ii`.

**3. MEDIUM — the whole native-integrity check vanishes instead of failing**
`sgs-check-native-block.sh:12`. If `native` is empty (dpkg-query pattern error suppressed by `2>/dev/null`, run inside a container/chroot, or a broken dpkg database), no `ok` or `bad` is emitted at all — the section silently disappears and a summary consumer sees one fewer check, not a failure. *Fix:* `else bad "no NVIDIA/CUDA/Docker packages found to verify"`.

**4. MEDIUM — kernel modules likely outside dpkg --verify's coverage (unverified)**
`sgs-check-native-block.sh:1-6` claims coverage of "the driver's … kernel modules", but `dpkg --verify` only checks files listed in package `md5sums`. DKMS-built `nvidia.ko` (the common install path when the prebuilt `linux-modules-nvidia-*` doesn't match the running kernel) has no md5sums record, and I am not certain the prebuilt module packages ship md5sums for `/lib/modules` entries. A replaced module — a stronger persistence primitive than a swapped `libcuda.so` — would then PASS. *Fix:* additionally hash the loaded module: `modinfo -n nvidia` + sha256 against a value recorded at install time.

**5. MEDIUM — wait_for_apt stalls on any open fd, and lock-timeout expiry kills the installer mid-install**
`install-apt.sh:8`. `fuser` reports *any process with the file open*, not lock holders: a monitoring agent running `dpkg-query`, a backup reading `/var/lib/dpkg/lock`, or sgs-check running concurrently will spin the loop the full 20 minutes and then `die` on a healthy machine. Conversely (line 6) if `fuser` (psmisc) isn't installed there is no wait at all and the original exit-100 recurs. And when `DPkg::Lock::Timeout=600` expires (unattended-upgrades routinely runs >10 min on a slow first boot), `apt-get` exits 100; under `set -e` the installer dies between `unpack` and `configure`, leaving half-configured packages — worse than not starting. *Fix:* detect actual lock holders (`lsof /var/lib/dpkg/lock-frontend` or `/proc/locks`), and wrap `apt_get` in a retry that on exit 100 runs `dpkg --configure -a` and retries rather than aborting.

**6. MEDIUM — ptrace_scope=1 breaks profiling/attaching to sibling training processes**
`files/sysctl-60-sgs.conf:8-9` and the check at `sgs-check-kernel-block.sh:3-4`. Yama scope 1 only permits attaching to *descendants*. `torchrun`/DDP workers, NCCL debug tooling, and `py-spy dump --pid` on a peer rank are siblings, not children — a routine ML debugging workflow fails with "operation not permitted" and sgs-check gives no hint why. *Fix:* either document/ship a `yama_ptrace_scope` group-based relaxation (2 with a `ptrace`-capable group via `/proc/sys/kernel/yama/ptrace_scope` scope 2 + group file), or have sgs-check WARN (not just the conf comment) that cross-rank attach needs sudo.

**7. LOW — userns behavioral test false-PASSes inside containers (unverified)**
`sgs-check-kernel-block.sh:18,20`. If sgs-check is run inside a Docker/K8s pod (plausible for a posture audit tool), `unshare -Ur` fails due to the container's seccomp policy, not host hardening → PASS reported while the *host* may have `apparmor_restrict_unprivileged_userns=0`. *Fix:* detect containerization (`/.dockerenv`, `systemd-detect-virt -c`) and downgrade to WARN "cannot test userns from inside a container".

**8. LOW — check enforces a value the config deliberately refuses to pin**
`sgs-check-kernel-block.sh:4` requires `perf_event_paranoid >= 2`, but `files/sysctl-60-sgs.conf:10-11` explicitly declines to pin it and tells users to lower it for Nsight. A user following the stack's own documented tuning gets `bad "Kernel hardening settings loosened"`. *Fix:* drop it from the enforced list or report it as informational.

## Explicit "no issue"

- **`-` sysctl prefix** (`files/sysctl-60-sgs.conf:33-34`): both procps `sysctl --system` and `systemd-sysctl` on 24.04 support the `-` ignore-missing prefix; no defect found. (Note it also silently swallows *permission* failures, but sgs-check's behavioral test at lines 18–24 covers the userns keys, so this is compensated.)
- **Rootless containers/snaps under `restrict_unprivileged_userns=1`**: Ubuntu 24.04 already ships these sysctls at 1 by default, so the stack introduces no regression beyond the distro default; snapd and podman ship profiles permitting userns (the podman one unverified).
- **`unprivileged_bpf_disabled` check `>=1` vs conf value 2** (`sgs-check-kernel-block.sh:3` vs conf:17): `>=` makes this correct.
- **`fuser` on a not-yet-existing `/var/lib/apt/lists/lock`**: fuser errors → treated as "free", which is correct.
