# deepseek/deepseek-v4.1-flash-1017

1. **High — sgs-check never finds the Jupyter process, so the new token and NoNewPrivs checks are skipped.** `sgs-check:545` and `sgs-check:563` identify Jupyter by grepping `ss -p` output for `jupyter`; `ss -p` prints the process comm, which for the `jupyter` console script is the Python interpreter (`python3`/`python3.12`), so `jup` and `jpid` are empty. Scenario: `sgs-jupyter@user` runs with passwordless sudo and no `NoNewPrivileges`; `sgs-check` prints “JupyterLab isn't running” and never runs the checks at `sgs-check:553-568`. Fix: identify the service by `systemctl show -p MainPID sgs-jupyter@*` or by the listening port, not by process name.

2. **High — sgs-check executes the stack Python as root before checking for unrecorded startup code.** `sgs-check:320-338` runs `"$PY" -I -c ...` as root; `-I` does not disable `site`, so `.pth` files and `sitecustomize.py` in `/opt/sgs/venv/.../site-packages` execute. The unrecorded-file check is later at `sgs-check:377`. Scenario: an attacker who can write to site-packages drops `evil.pth`; `sudo sgs-check` executes it as root before reporting it. Fix: run stack Python as an unprivileged user, or inspect metadata with `-S`/without executing site, or run the unrecorded check before any stack-Python invocation.

3. **High — apt source boolean bypass: `trusted=1` / `allow-insecure=1` is not detected.** `sgs-check:74` lists unsafe options, but `sgs-check:82` and `sgs-check:99` only match the literal value `yes`. apt accepts `1` (and likely `true`/`on`) as true. Scenario: `/etc/apt/sources.list.d/evil.list` contains `deb [trusted=1] http://evil/ ...`; apt installs unsigned packages, while sgs-check reports the source as safe. Fix: parse apt booleans case-insensitively, including `1`, `true`, `on`, `with`, and treat any non-`no`/`false`/`0` as unsafe.

4. **Medium — Jupyter token journal check only looks at the current service start, but the token is reused.** `files/sgs-jupyter@.service:19` reuses `~/.local/share/jupyter/sgs-token` across restarts; `sgs-check:571-577` greps only `journalctl --since "$since"` for the current `ActiveEnterTimestamp`. Scenario: the first start logs the token; the service restarts; the same token remains valid, but sgs-check reports “token stays out of the journal.” Fix: grep the whole journal for the current token value, or rotate the token on every start.

5. **Medium — file integrity check passes with zero claims if RECORD files are removed.** `sgs-check:496-497` prints `PASS|All 0 installed files match...` when `claims` is empty. Scenario: an attacker with write access to site-packages deletes all `*.dist-info/RECORD` files; sgs-check reports PASS instead of noticing that it has nothing to verify. Fix: fail or warn when `claims` is empty, or when expected distributions are missing.

6. **Medium — deleting `/opt/sgs/files.sha256` silently disables the stack-file integrity check.** `sgs-check:512-516` only runs the check `if [ -f /opt/sgs/files.sha256 ]`; there is no `else`. Scenario: an attacker removes or renames the manifest; sgs-check gives no warning about the startup hook, commands, or Jupyter unit. Fix: warn when the stack is installed but `files.sha256` is missing.

7. **Medium — NoNewPrivs check only inspects one Jupyter PID.** `sgs-check:563-568` takes `head -1` from `ss -p`. Scenario: the systemd service has `NoNewPrivileges=yes`, but a user-run Jupyter on `127.0.0.1:8889` does not; sgs-check checks the service PID and reports PASS while the user-run Jupyter can still `sudo`. Fix: check every listening Jupyter PID, or every `sgs-jupyter@*` unit.

8. **Medium — installer calls `lspci` before installing `pciutils`.** `install.sh:108-115` runs `lspci` in preflight, but `pciutils` is installed only at `install.sh:109` after that. Scenario: on a minimal Ubuntu 24.04 image without `pciutils`, `lspci` is missing, `GPU_COUNT=0`, and `install_driver` skips the NVIDIA driver entirely. Fix: install `pciutils` before the GPU probe, or check for `lspci` and install it first.

9. **Medium — a failed Jupyter restart aborts the installer before audit rules and manifest are written.** `install.sh:523-527` runs `systemctl restart "sgs-jupyter@${TARGET_USER}"` under `set -e`; if the service fails (e.g. bad `HOME`, token directory permission), the script exits before `install_audit_rules` and `write_manifest` at `install.sh:595-596`. Scenario: Jupyter fails to start; the machine is left without `/etc/audit/rules.d/60-sgs.rules` and `/opt/sgs/files.sha256`. Fix: guard the restart with `|| info ...` or continue the install and report the failure.

10. **Medium — `sgs-venv` ownership check is only top-level and `chmod go-w` is not recursive.** `bin/sgs-venv:22-28` checks only `stat -c %u "$1"` and then `chmod go-w "$1"`. Scenario: a user-owned directory is group/world-writable or already contains an attacker-owned `lib/python3.12/site-packages`; the script writes `sgs-stack.pth` there, and the attacker can swap it after creation. Fix: require an empty/new directory or recursively verify ownership and permissions, and use `chmod -R go-w`.

11. **Medium — Jupyter token file permissions are not enforced if the file already exists.** `files/sgs-jupyter@.service:19` creates the token with `umask 077`, but if `~/.local/share/jupyter/sgs-token` already exists with mode `0644`, it is used unchanged. Scenario: another local user reads the token and connects to Jupyter through localhost or a tunnel. Fix: `chmod 600` the token file before reading it, or create it with `install -m 600`.

12. **Medium — deb822 parser ignores or mangles continuation lines, so a second URI can evade the source check.** `sgs-check:85-101` treats any indented continuation as `fields[last] = fields[last] or "(inline key)"`. Scenario: a `.sources` file has `URIs: https://ubuntu.com/ubuntu` followed by an indented `http://evil/`; apt uses both, but sgs-check only checks the first and reports PASS. Fix: append stripped continuation lines to the previous field value, and handle inline `Signed-By` keys separately.
