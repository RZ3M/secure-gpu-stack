# z-ai/glm-5.3-flash

## Findings (most severe first)

**1. High — the Jupyter token is written to the system journal by Jupyter itself, so the shipped default fails its own audit**
`files/sgs-jupyter@.service:26` passes the token via `JUPYTER_TOKEN`, but Jupyter's startup banner (`Jupyter Server is running at: http://…?token=<token>`) logs the *actual* token regardless of who supplied it — your own comment at lines 22–24 admits this ("a token it was given shows up there as `token=...`"). Scenario: fresh install → `journalctl -u sgs-jupyter@ubuntu` (readable by every member of `adm`, i.e. typically every admin/sudo account on a shared GPU box) contains the live token → that account reads/edits all notebooks and can run arbitrary code as the user. Your sgs-check line 62–64 will correctly report **bad** on a stock install, meaning either the product ships red or users learn to ignore the auditor. Fix: run Jupyter with `--log-level=WARN` (the banner is an INFO log record) or use an identity-provider/hash so the plaintext token never appears in `server_info`, then keep the check.

**2. High — sgs-check false PASS for Jupyter started under another process name (contradicts the script's own claim)**
`sgs-check-jupyter-block.sh:3,43` find Jupyter only via `ss ... | grep -i jupyter`, and the header comment (lines 1–2) explicitly claims `python -m jupyterlab` can't hide. But `ss -p` shows the **comm**, which for `python -m jupyterlab` (or a Jupyter launched by the VS Code Remote-SSH/Jupyter extension) is `python`, not `jupyter`; the MainPID loop (lines 4–5, 44–45) only covers `sgs-jupyter@*` units. Scenario: user follows the Lambda dashboard habit and runs `jupyter lab` via VS Code → binds 127.0.0.1:8888 (or, with `--ip 0.0.0.0`, the network) → sgs-check prints "JupyterLab isn't running" and everything PASSes. Fix: enumerate candidate PIDs from `/proc/*/cmdline` (match `jupyter`, `jupyterlab`, `jupyter_server`) instead of `ss` process names.

**3. High (workflow) — the socket design breaks the documented Lambda/user paths, pushing users back to insecure localhost**
Lambda Cloud's dashboard "Jupyter" link and VS Code's Ports panel forward **TCP ports**, not Unix sockets; Windows OpenSSH's support for `-L 8888:/run/...` (streamlocal forward) is version-dependent and historically broken (**unverified** which builds work). Scenario: Lambda user opens the dashboard link → connection refused; VS Code user clicks "forward port 8888" → nothing listening; the path of least resistance is `jupyter lab` on 127.0.0.1 — which, per finding 2, sgs-check can't see. Fix: ship a `sgs-tunnel` helper (prints a client-side command per OS, with a plain-TCP local relay option), document the dashboard limitation loudly at install time, and make sgs-check detect non-stack Jupyter reliably (fix 2) so the fallback can't silently regress.

**4. Medium — no sgs-check for the sshd settings the whole design depends on**
The access model requires `AllowStreamLocalForwarding` (default `yes`, confirmed on krabs) and the absence of `DisableForwarding yes`; `sshd_config` on Lambda images or by an admin `AllowStreamLocalForwarding no` / `DisableForwarding yes` (or a `Match User` block with `ForceCommand`-style restrictions) makes every `-L ...:socket` tunnel fail with a confusing channel-open error while sgs-check reports all-green. Fix: add a check on `sshd -T` output for `allowstreamlocalforwarding`/`disableforwarding` and for per-user `Match` blocks affecting the target users.

**5. Medium — token audit checks only the first socket, and only unauthenticated access on it**
`sgs-check-jupyter-block.sh:31` (`head -1`) tests auth on one socket; with two sockets (stack unit + user-run second instance, or `jup_sock` containing a stale entry), a second Jupyter with `allow_unauthenticated_access=True` is not probed and line 36 prints PASS. Fix: loop over every entry in `$jup_sock` and require 401/403 from each; also probe `/api/contents` and a `/lab` GET, not just `/api/kernels`.

**6. Medium — sgs-check's ss parsing is fragile across ss versions/paths**
`sgs-check-jupyter-block.sh:8` assumes the unix-socket path is exactly field `$5` of `ss -xlpnH` and that no path contains whitespace; on some ss builds the column layout differs (and a username with a space — possible via `useradd -c`-independent custom NAME_REGEX setups, unverified — shifts fields). Failure mode is a silent false PASS ("JupyterLab isn't running"). Fix: parse with `ss -xlpnH` plus `ss -xp` JSON output (`ss -xlp -0` … or `ss --json`) instead of positional awk, or verify the claimed path exists with `find /run/sgs-jupyter -name jupyter.sock -type s` independently.

**7. Medium — `sgs-jupyter` prints the live token to the terminal**
`bin/sgs-jupyter:24` embeds the token in the printed URL. Scenario: user runs it inside VS Code's integrated terminal / tmux / `tee install-log` → token sits in scrollback, session logs, or a pasted support ticket; anyone with a later screenshot or log gets full Jupyter access (and through it code execution as the user). Fix: print only the file path and the tunnel command; give a one-liner (`curl`-free) like `echo "token: $(cat ~/.local/share/jupyter/sgs-token)"` the user runs at paste time, or omit the token from step 2's URL and say "add ?token=$(cat …)".

**8. Medium — user-checks asserts unauthenticated `/api` returns 200, which conflicts with the hardening it's testing**
`tests/user-checks.sh:54–55` expects HTTP 200 on `/api` **without a token**, while the service sets `allow_unauthenticated_access=False` (`sgs-jupyter@.service:26`). If jupyter_server 2.21 actually gates `/api` (**unverified** — your note says 403 was observed on `/api/kernels`), this check fails on every secure machine; if `/api` is genuinely exempt, it confirms an unauthenticated endpoint that leaks server metadata. Fix: decide and encode one behavior — assert 403 without token and 200 with token (read the token from the file).

**9. Low — stale `sgs-token` file can be anything**
`sgs-jupyter@.service:26` trusts any non-empty `~/.local/share/jupyter/sgs-token` (from a previous manual `jupyter lab` run, a truncated write, or a user-generated "password" like `12345678`). A weak attacker-chosen token defeats the token gate entirely while sgs-check's journal greps still PASS. Fix: validate the file against `^[0-9a-f]{48}$` and regenerate otherwise; optionally refuse tokens shorter than N bits with a warning in sgs-check (readable only via the user's file, so only self-inflicted).

**10. Low — attack-demo's socket probe hardcodes the tester as the socket owner**
`tests/attack-demo.sh:40,49` forwards to `/run/sgs-jupyter/$USER_NAME/jupyter.sock`, so on a multi-user machine testing with the default `ubuntu` account validates only that user's instance; another user's service is never exercised, and if the target user has no unit running the tunnel test fails confusingly. Fix: after login, resolve the socket via the target user's `sgs-jupyter` output (`on_host 'sgs-jupyter'`) rather than constructing the path client-side.

**No issue** on: the `/run/sgs-jupyter` symlink/race angle (parent is root-owned, subdirs are the same user the service runs as, so no crossing of privilege boundaries), the ipc kernel connection files (umask 077 at `ExecStart` covers them, dir is 0700), or the hard-coded `tcp://127.0.0.1` kernel port (key lives in the 0700 folder).
