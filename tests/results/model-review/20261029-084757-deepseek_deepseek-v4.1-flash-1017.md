# deepseek/deepseek-v4.1-flash-1017

1. **High — Docker port publishing can bypass the firewall; “localhost only” is not enforced by the threat model.** The doc claims Docker publishes to localhost only (`docs/threat-model.md:24`) and treats containers as contained (`:27`), but a user or malicious image can run `docker run -p 0.0.0.0:8888:8888`; Docker’s iptables rules commonly bypass UFW. Scenario: a notebook/container exposes an internal service to the internet despite “firewall denies incoming except SSH.” Fix: configure Docker with `iptables=false`/rootless networking or enforce loopback-only publishes, and make `sgs-check` fail on any non-loopback published port.

2. **High — Shared GPU use is not a security boundary; MIG is untested and not required.** The model says GPU files are `video`-only (`docs/threat-model.md:26`) but for a small team all GPU users likely land in `video`; MIG/NVSwitch/NVLink are explicitly untested (`:64-66`). Scenario: one team member or malicious package opens the GPU, exhausts/resets it, or uses another MIG instance if isolation is misconfigured. Fix: require per-user MIG or cgroup/device isolation for multi-user hosts, and have `sgs-check` verify MIG mode and GPU assignment rather than only file permissions.

3. **High — Cloud metadata service is not blocked from notebooks or containers.** The firewall section only covers inbound (`docs/threat-model.md:24`) and outbound is unrestricted (`:43`). Scenario: a malicious pip package or model runs `curl 169.254.169.254` and steals instance credentials, if Lambda exposes metadata (unverified for Lambda specifically). Fix: block link-local/metadata from user and container networks by default, and add an `sgs-check` probe.

4. **High — Hugging Face/W&B/cloud tokens are readable by any code running as the user, with unrestricted egress.** Credentials are listed as valuable (`docs/threat-model.md:13-14`), but the malicious-package row (`:25`) and “your own code” caveat (`:39-42`) leave token theft unmitigated. Scenario: `pip install` or `trust_remote_code` reads `~/.cache/huggingface/token`, `~/.netrc`, or env vars and exfiltrates them. Fix: document scoped/short-lived tokens, enforce token-file permissions, scan for world-readable secrets in `sgs-check`, and pair with outbound restriction.

5. **High — Release signature is optional and key custody is undecided.** The installer trusts a checksum plus “optional signature” (`docs/threat-model.md:28`), and “who holds the release signing key isn’t decided” (`:67`). Scenario: a compromised download host serves both a malicious installer and matching checksum; unsigned installs pass. Fix: require a valid signature by default, fail closed, and define key custody/rotation before claiming tamper resistance.

6. **High — Model/dataset download paths can execute code despite `torch.load` hardening.** The model claims `torch.load` refuses code and `modelscan` is installed (`docs/threat-model.md:25`), but Hugging Face `trust_remote_code=True`, dataset loading scripts, and pickle-bearing artifacts bypass that. Scenario: a downloaded model repo runs arbitrary Python as the user and reads tokens/data. Fix: disable/document `trust_remote_code`, prefer `safetensors`, scan caches, and make `sgs-check` flag unsafe model-loading config.

7. **Medium/High — SSH agent forwarding is allowed and TCP forwarding is not restricted.** The doc admits `ssh -A` is allowed and root can use the agent (`docs/threat-model.md:51-53`), while only X11 is disabled (`:24`). Scenario: a compromised server/root uses the forwarded agent, or `ssh -R` exposes an internal socket/metadata to a remote host. Fix: disable `AllowAgentForwarding` and restrict `AllowTcpForwarding`/`GatewayPorts` by default; `sgs-check` should report them.

8. **Medium/High — Malicious packages can persist via user systemd units, cron, or shell rc files.** The model says notebook code is sandboxed (`docs/threat-model.md:25`) but “your own code” runs as you (`:39-42`); user-level persistence is not addressed. Scenario: a package writes `~/.config/systemd/user/*.service` plus linger, or a cron job, and survives the notebook. Fix: disable linger, audit user units/cron/rc files in `sgs-check`, and document that user-level persistence is outside the notebook sandbox.

9. **Medium — Core dumps, swap, and `/dev/shm` can retain secrets after a job.** The model protects credentials and data (`docs/threat-model.md:11-14`) but does not mention crash dumps, swap, or shared memory. Scenario: a process holding an HF token crashes into a readable core dump, or `/dev/shm` keeps model/token fragments after the job. Fix: disable core dumps, use encrypted/no swap, clear `/dev/shm` on logout/job end, and add `sgs-check` checks.

10. **Medium — “Jupyter has no port at all” is contradicted by the known ipykernel localhost TCP port.** The table says Jupyter has only a private socket (`docs/threat-model.md:24`), but the known gap says one localhost TCP port per kernel remains (`:61-63`). Scenario: another local user scans/connects to the kernel port; the random key helps but the port is still reachable and DoS-able. Fix: clarify the claim, prefer Unix sockets, and firewall/owner-match kernel ports; `sgs-check` should verify.

11. **Medium — “Even root’s GPU use can’t reopen” GPU device files is stronger than a hardening stack can deliver.** The doc says GPU files are locked so even root can’t reopen them (`docs/threat-model.md:26`), then correctly says root can undo every setting (`:36-37`). Scenario: root chmods/chowns device nodes or reloads modules; the claim misleads users into thinking GPU isolation survives root. Fix: reword to “non-root users cannot reopen without privilege”; root compromise is out of scope.

12. **Medium — NCCL/multi-node traffic is excluded as “Lambda’s side” but is user-visible and unauthenticated/plaintext.** The model excludes the network between machines (`docs/threat-model.md:49-50`) and outbound is unrestricted (`:43`). Scenario: multi-node training sends gradients/activations over provider network without app-layer auth/encryption; a compromised co-tenant or node can intercept/inject. Fix: document NCCL’s lack of transport security and require WireGuard/IPsec or trusted isolated networking for multi-node jobs; add a deployment check.
