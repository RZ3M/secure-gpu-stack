# z-ai/glm-5.3-flash

## Round Y findings

**1. HIGH — Lockdown set at install time can brick the GPU after a later DKMS appearance.**
`setup_lockdown` (install.sh:47–49) only checks `dkms status` once, at install. Scenario: install with Ubuntu's signed prebuilt `linux-modules-nvidia` → lockdown cfg written. Weeks later the user installs any DKMS module (v4l2loopback, zfs, or a kernel update triggers `dkms autoinstall` for a previously "added" module) → next boot lockdown refuses it → device silently gone. The only detection is sgs-check's journal grep (sgs-check:60), which is fragile (see #3). Fix: have sgs-check actively verify expected devices/modules (e.g. `nvidia-smi` works, `dkms status` modules are loaded) rather than relying on one log string, and have install.sh leave a persistent marker that warns on every login while DKMS modules and lockdown coexist.

**2. HIGH — sgs-check reports "skip", not "bad", when lockdown state is unreadable (sgs-check:79).**
If securityfs isn't mounted, the `lockdown` LSM is missing from `lsm=` (a hardening step that edits kernel settings could plausibly touch this), or a custom kernel lacks CONFIG_SECURITY_LOCKDOWN_LSM, `lockdown` is empty → `*) skip "Couldn't read the kernel lockdown state"`. The machine has zero lockdown protection and the daily check never fails. Fix: treat unreadable/empty lockdown state as `bad` ("couldn't verify lockdown — assume off"), not skip.

**3. HIGH — Refusal detection hinges on one exact journal string (sgs-check:60).**
`grep -q 'unsigned module loading is restricted'` — the kernel's lockdown denial message wording varies across versions and subsystems (unverified exact string for module loading vs. `/dev/mem`/kexec denials), and `journalctl -k` can be empty (journal not persistent, or the check runs in a context without it). A refused module then yields the `ok` branch (sgs-check:69): "Kernel lockdown is on … even root can't load unsigned modules" — PASS while the GPU is dead. Fix: match broadly (`Lockdown:.*restricted`) *and* independently verify the NVIDIA module actually loaded this boot.

**4. HIGH — Startup-record fallback silently accepts tampering (install.sh:111–113 + sgs-check:115–118).**
If install.sh's `sgs-check --accept-changes` fails (only an `info` is printed), no record exists; the first later sgs-check run then creates the record itself (sgs-check:115–118) with no review. Any startup-file modification made between install and that first run is accepted as the trusted baseline. Fix: make install.sh fail loudly (or retry) if the record can't be created, and make sgs-check's implicit first-record path require `--accept-changes` too (or stamp the record with the install version and flag records not created at install time).

**5. HIGH — Watched-file list misses classic root/persistence locations, so the "ok" message overstates coverage (sgs-check:17–39).**
Not watched: `/etc/ld.so.preload` (the textbook rootkit persistence), `/etc/sudoers` itself (only `sudoers.d/*`), `/etc/profile.d/*`, `/etc/systemd/system/*`, `/etc/init.d/*`, `/etc/rc.local`, `/etc/udev/rules.d/*`, `/etc/modprobe.d/*`, `/etc/ssh/sshd_config.d/*`. An attacker (or malicious container escape / pip post-install script running as root) dropping `/etc/profile.d/x.sh` or a systemd unit changes nothing sgs-check watches → "No cron job, shell startup file, user service or SSH key changed" (sgs-check:111). Fix: add these paths to `startup_files`.

**6. MEDIUM — Failed `update-grub` leaves lockdown armed for a later unrelated boot (install.sh:54, 81–82).**
Both failure paths only print a warning. Scenario: `update-grub` fails during install (chroot-like state, broken hook); cfg file remains installed; a later kernel update regenerates grub.cfg; meanwhile a DKMS module appeared → next reboot refuses it → broken GPU with no connection to the install that set it. Fix: on `update-grub` failure, remove the cfg (roll back) or verify `lockdown=integrity` actually landed in `grub.cfg` before declaring success.

**7. MEDIUM — Secure Boot machines get no cfg fallback, so disabling SB later leaves lockdown permanently off (install.sh:67–71).**
When lockdown is on from Secure Boot, install.sh returns without writing the cfg. If Secure Boot is later turned off (firmware toggle, or a pending `mokutil --disable-validation` an attacker with brief root/console sets up), the next boot has no lockdown and no cfg to restore it; sgs-check reports bad but nothing repairs it. Fix: always install the cfg — `lockdown=integrity` on the cmdline is harmless (idempotent) under Secure Boot.

**8. MEDIUM — Paths with spaces break the record comparison (sgs-check:82, 89, 107, 109).**
`awk '{ print $2 }'` truncates at the first space. A home directory like `/home/john doe` yields path `/home/john`; a modified file under such a home can compare "unchanged" (its truncated path matches the record) → PASS on a tampered `.bashrc`/`authorized_keys`. Fix: parse with `while read -r hash path` (paths are the remainder of the line) or NUL-delimit.

**9. MEDIUM — "lockdown is on" can be reported when the cmdline value is not integrity (install.sh:83–84, 56–57).**
If the machine's own GRUB settings contain `lockdown=none` (or a typo like `lockdown=integrity` on a kernel that doesn't support it), install.sh:56–57 says "so it stays" and sgs-check's `none` branch is the only catch — while the user believes the stack enforced lockdown. Also install.sh:83–84: after writing the cfg, if `/proc/cmdline` already contains any `lockdown=` token, it prints "Kernel lockdown is on ($lockdown)" — which can literally read "is on (none)". Fix: parse the actual value from `/sys/kernel/security/lockdown` and only claim "on" for integrity/confidentiality.

**10. MEDIUM — `--no-lockdown` is ineffective when the user's own GRUB sets lockdown (install.sh:56–57).**
The opt-out removes only the SGS cfg; a `lockdown=` in `/etc/default/grub` "stays". Combined with DKMS modules present, the user who explicitly opted out still gets unsigned modules refused after reboot — a broken machine the option was supposed to prevent. Fix: detect the user's own `lockdown=` in this branch and either offer to remove it or fail with a clear instruction instead of an informational note.

**11. MEDIUM — Recovery-mode boots bypass the lockdown setting.**
The cfg appends to `GRUB_CMDLINE_LINUX_DEFAULT` (grub-60-sgs-lockdown.cfg:7), which GRUB omits for recovery-mode entries. Anyone with console access (common on rented-bare-metal return/reimage flows, or a colocated box) reboots into recovery → lockdown off → unsigned module load. Fix: append to `GRUB_CMDLINE_LINUX` instead (applies to recovery too).

**12. LOW / unverified — Symlink fingerprints silently drop unreadable targets (sgs-check:8–9).**
`[ -f "$1" ] && cat "$1"` under `2>/dev/null`: if sgs-check ever runs unprivileged (e.g. a user-run variant) and the symlink target is root-only, the fingerprint is just the readlink hash — later content changes to the target go undetected and the check reports "No … changed". Unverified whether sgs-check can run non-root; fix: emit a distinguishable "unreadable" fingerprint instead of silently hashing the link text alone.
