Findings, ranked. All are grounded in the two scripts as given; the one behavioural claim I can't confirm is marked unverified.

1. MEDIUM — sgs-check:588,606: every Jupyter-specific check (token required at 599-603, no-new-privileges/sudo at 606-613, token-in-journal at 618-631, token-file perms at 628-630) is gated on `grep -i jupyter` matching the process name that `ss -p` prints, which is the process comm (e.g. "python3" for a Python interpreter), not the command line. Scenario: `sgs-jupyter` execs a Python interpreter whose comm doesn't contain "jupyter" → `jup` is empty, the section prints only the note "JupyterLab isn't running" (590), and a Jupyter that answers without a token and without NoNewPrivileges produces zero WARNs — a machine passing every other check. Unverified: whether the (unseen) sgs-jupyter wrapper/service leaves a comm containing "jupyter"; the docker-proxy match at 573 shows the author relies on comms elsewhere. Fix: identify the Jupyter PIDs structurally — `systemctl show -p MainPID 'sgs-jupyter@*'` (fall back to the listening port's owner uid) — and gate the checks on that, keeping the ss grep only as a fallback.

2. MEDIUM — sgs-check:360-372: the "stack is read-only" perimeter covers only `/opt/sgs/venv` (site-packages at 360, bins at 367); `/opt/sgs/tools` (pip-audit, modelscan — symlinked onto PATH at install.sh:513) and `/opt/sgs/tf-cuda12` are never checked for ownership/writability, and the default `PIP_AUDIT=/opt/sgs/tools/bin/pip-audit` (430) gets no ownership check when `SGS_PIP_AUDIT` is unset (the guard at 432 applies only when it is set). Scenario: a local user who somehow gains write access to /opt/sgs/tools (an admin chmod, a changed install path) replaces pip-audit; the admin then runs sudo sgs-check, which executes it as `run_as` (443) — i.e. as the admin's own account. The comments at 405-406 and 431 still say "runs as root", contradicting the runuser at 443 — evidence the execution model was changed and the guard/checks weren't re-derived. Fix: extend the 360-372 loop to `/opt/sgs/tools` and `/opt/sgs/tf-cuda12` (dirs plus first-level contents), apply the 432 ownership guard to the default path too, and delete the stale "as root" comments.

3. LOW — install.sh:249-253 vs sgs-check:562-568: install deliberately supports sshd on extra ports (opens ufw for every port `sshd -T` reports) but sgs-check exempts only port 22, so a `Port 2222` listener held by sshd or its socket is flagged `bad "Listening to the network besides SSH"` forever. Scenario: admin adds Port 2222, install opens ufw for it, then sgs-check permanently fails the machine it just configured — the two scripts contradict each other. Fix: in sgs-check, exempt any listener whose process is sshd/systemd regardless of port (match the port set from `sshd -T` instead of the literal `:22`).

4. LOW — install.sh:104-107: the duplicate-source fixup runs only when the stack's own `.sources` file already exists, so on a first run it's unreachable before the `apt-get update` at 108. Scenario: a machine that already has two entries for the same repo with different Signed-By (e.g. docker.list from get.docker.com plus a hand-written docker.sources) → line 108 fails with apt's raw "Conflicting values set for option Signed-By" and set -e aborts the install, though setup_sources:184/200 could have moved the files aside. Fix: call `disable_duplicate_sources` unconditionally in preflight (drop the `[ -e ours ] &&` guards).

5. LOW — install.sh:94-97: the preflight "run me from an unpacked release" guard lists some files but not five that are consumed later: files/sshd-10-sgs.conf (231), files/docker-daemon.json (420), files/profile-sgs.sh (515), files/motd-60-sgs (521), files/sgs-jupyter@.service (522). Scenario: a truncated release → the install gets through sources, hardening, Docker and Python, then dies at 420 or 515-522 with a raw install/cp error, leaving a machine with the new Docker/SSH config but no audit rules, no manifest and no files.sha256 — sgs-check then reports the integrity record missing. Fix: add the five files to the 94-97 loop.

6. LOW — install.sh:525 vs 527-533: the invariant "a Jupyter that won't start mustn't stop the install before the audit rules and the file manifest are written" is enforced only for `restart` (guarded by `if`), while `systemctl enable` on the line above is unguarded under set -e. Scenario: any enable failure (masked unit, systemd not running during an image-build/chroot install — daemon-reload at 523 would also fail) aborts the script before install_audit_rules and write_manifest. Fix: `systemctl enable ... || info "Couldn't enable sgs-jupyter@${TARGET_USER}"`.

7. LOW — sgs-check:196-197 vs install.sh:325: `--no-driver` is a documented installer option, but on a GPU machine installed that way sgs-check reports `bad "GPUs present but no NVIDIA driver installed"` every run, so the stack's own audit tool permanently fails a configuration the installer supports. Fix: accept an explicit opt-out marker (e.g. a `/opt/sgs/no-driver` flag written by install.sh) and emit SKIP with the reason instead of WARN.

8. LOW — sgs-check:580: the "firewall lets these through" classification matches `ufw status` output by literal port prefix, so app-profile rules (`OpenSSH ALLOW Anywhere` style) never match; an exposed port actually allowed via an app rule yields the note "The firewall blocks all of these from the network" — a wrong, reassuring statement. Scenario: owner runs `ufw allow Nginx` for a listener on 8888 → sgs-check says the firewall blocks it. Fix: parse `ufw status verbose` app rows too, or use `ufw status` machine output (`--format`) keyed on port numbers.
