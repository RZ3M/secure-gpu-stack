# z-ai/glm-5.3-flash

# Round A findings — most severe first

## 1. HIGH — Jupyter service has no `NoNewPrivileges`, so notebook/malicious-package code execution becomes root
`files/sgs-jupyter@.service:9-16` runs Jupyter as the target user with only `PrivateTmp=yes`. On Lambda the target user *is* the passwordless sudoer (design.md:184-186 admits this). Any code execution inside Jupyter — a typosquatted package installed in a notebook, a poisoned kernel spec, a model-loading exploit — runs as `ubuntu` and can immediately `sudo` to root, then backdoor `/usr/local/bin/sgs-check` and the `.pth` hook so the machine's own audit tool reports PASS forever after.
**Fix:** add `NoNewPrivileges=true` to the unit (blocks setuid/`sudo` for the whole service tree; kernels and CUDA don't need it), plus `RestrictSUIDSGID=true`/`CapabilityBoundingSet=`; or run Jupyter as a dedicated non-sudo user.

## 2. MEDIUM — sgs-check flags only pins >1000; a low/negative pin that blocks noble-security passes every update check
`bin/sgs-check:131-137` warns only on `Pin-Priority > 1000`. A pin of `-1`, `1`, or `100` makes the candidate equal the installed version, so `apt list --upgradable` (499-500) shows nothing → "No pending security updates" PASS, and unattended-upgrades no-ops while still refreshing `upgrade-stamp` → "completed a run in the last 3 days" PASS (509-516). Scenario: a malicious deb's postinst or a "tuning" script drops `/etc/apt/preferences.d/99-block-security` with `Pin: release n=noble-security`, `Pin-Priority: 100`, scoped to `linux-* openssh-* libssl*` (a `Package: *` pin would trip the driver check at 166-171, so scope it). Machine stays unpatched with zero warnings.
**Fix:** also flag pins ≤100 that change candidates for ubuntu.com suites, or verify with `apt-get -s dist-upgrade` that nothing is held.

## 3. MEDIUM — audit rules don't record what sgs-check claims: directory watches miss file edits and subdirectories
`install.sh:540-548` uses `-w /etc/apt/ -p wa`, `-w /etc/docker/`, etc. Audit watches are per-inode and non-recursive: they catch entries created *directly in* the watched dir, but **not** edits to existing files (`/etc/docker/daemon.json`, `/etc/apt/sources.list`) and **not** anything in subdirectories (`/etc/apt/sources.list.d/`, `preferences.d/`, `apt.conf.d/`). `sgs-venv` and `sgs-jupyter` aren't watched at all (546 watches only `sgs-check`). Scenario: a malicious postinst adds `sources.list.d/evil.sources` and flips `default-runtime` to `nvidia` — `ausearch -k sgs-` shows nothing, yet sgs-check:479 PASSes "Audit log records changes to package sources, sudo, SSH, Docker…".
**Fix:** add explicit watches for the subdirectories and the individual files (`daemon.json`, `sources.list`, `sgs-venv`, `sgs-jupyter`).

## 4. MEDIUM — locale-dependent parsing: installer aborts on non-English systems; sgs-check can report a false PASS
`install.sh:395` parses `apt-cache policy` for `Candidate:`; apt translates that label ("Candidat :", …), so on a non-English locale `nccl_ver` is empty and line 398 `die`s — after driver and Docker are installed, leaving a half-installed machine (re-run needed with `LC_ALL=C`). Same class in sgs-check: `apt list --upgradable | grep 'upgradable from'` (499-500) matches nothing when translated → **"No pending security updates" PASS with updates pending**; `ufw status | grep "Status: active"` (426, 461-463) fails → false "Firewall is off" WARN; `apt-cache policy` at 168 → false "driver blocked" WARN. (apt/ufw localization of these exact strings: verify on a non-English locale.)
**Fix:** run all output-parsing commands under `LC_ALL=C`.

## 5. MEDIUM — any hostname ending in `ubuntu.com` is treated as Ubuntu's own
`bin/sgs-check:101` exempts sources whose host `endswith("ubuntu.com")` from the HTTPS/signed-by scrutiny — `notubuntu.com` and `evil-ubuntu.com` both match. Line 166 has the same flaw: the driver-freshness check greps `apt-cache madison` output for `ubuntu\.com`, so a repo on a lookalike host counts as "Ubuntu's newest". Scenario: a planted `deb http://notubuntu.com noble main` with a per-source attacker key is invisible to the sources check and the global-key check stays clean → all PASS while apt installs attacker packages; the same host in madison makes a backdoored `nvidia-utils` look like a legitimate "driver update waiting" (social-engineers the admin into installing it).
**Fix:** require the host to end in `".ubuntu.com"` (or an explicit allowlist of Ubuntu's hosts).

## 6. MEDIUM-LOW — the flagship integrity check doesn't cover the stack's non-pip files, including the startup hook
`install.sh:500,512,514` place `sgs-cuda-preload.pth`/`sgs_cuda_preload.py` (executed by **every** Python process in the venv, Jupyter included), `sgs-venv`, `sgs-jupyter` and the unit file on disk outside pip, so they appear in no RECORD and sgs-check's hash check (362-414) ignores them: it still prints "All N installed files match" (403) after they're replaced. Audit covers only the `.pth` pair and `sgs-check` (545-546) — and per finding 3 that log is the only detective control. Scenario: brief root compromise swaps `sgs_cuda_preload.py` for a version that exfiltrates/exects in every training run; integrity check PASSes.
**Fix:** record SHA-256 of these files in `/opt/sgs/manifest.txt` at install and verify them in sgs-check.

## 7. LOW (unverified) — unattended-upgrades origin patterns for NVIDIA may never match, and nothing checks it
`install.sh:276-279` relies on `"origin=NVIDIA,label=NVIDIA"` matching NVIDIA's flat repo (`Suites: /`) Release file. If NVIDIA's actual Origin/Label differ, Container Toolkit/cuDNN fixes never auto-install — exactly the gap design.md:224-228 claims to close — while sgs-check:505 only verifies that unattended-upgrades is "on".
**Fix:** verify the Release file's Origin/Label; add a check that the installed third-party origins are actually covered (e.g., dry-run unattended-upgrades and inspect what it would take).

## 8. LOW — daemon.json merge preserves a hostile `default-runtime: "nvidia"` on re-run
`install.sh:422` (`current.update(ours)`) keeps the owner's existing keys, including `default-runtime: "nvidia"` — a setting common in GPU-docker guides that gives every container the toolkit's host-side hooks without `--gpus` (the NVIDIAScape/CVE-2025-23266 path, per sgs-check:238-242). The installer completes claiming secure defaults; only sgs-check's WARN reveals it.
**Fix:** override or refuse unsafe keys (`default-runtime`, `iptables: false`) the way conflicting sources are handled.

## 9. LOW — the pip index check only greps for `extra-index-url`
`bin/sgs-check:297-303` never looks at `index-url`: a pip.conf (or `PIP_INDEX_URL`) pointing the *primary* index at an attacker-controlled mirror passes as "pip uses a single package index", and `PIP_EXTRA_INDEX_URL` set in a shell profile or the Jupyter environment bypasses the file grep entirely — both restore the torchtriton-style dependency-confusion path the check exists to catch.
**Fix:** also flag a non-PyPI `index-url` and document that env overrides exist (or unset them in the Jupyter unit).

## 10. LOW — `sgs-venv` builds into attacker-writable directories
`bin/sgs-venv:21-31` creates the venv wherever the user says. If the path is a shared/pre-created dir (e.g., another user pre-creates `/tmp/env` mode 777), that user can swap `bin/python` or rewrite the generated `sgs-stack.pth` (25) after creation → code execution as the victim on next use.
**Fix:** refuse paths that are world-writable or writable by group/other; `chmod 700` the venv.

## 11. LOW — `/dev/nvidia*` stays 0666
design.md:273-276 defers `NVreg_DeviceFileMode=0660`, so on any shared box every local user (and every container process) can open the GPU devices — the local-driver attack surface NVIDIA bulletins keep patching, plus cross-user GPU access. Nothing in `files/modprobe-sgs-nvidia.conf` (per design.md:246-250 it sets only `RestrictProfilingToAdminUsers`) or sgs-check reports the device mode.
**Fix:** ship the 0660 + gpu-group setting now, or at least have sgs-check report `/dev/nvidia*` permissions.
